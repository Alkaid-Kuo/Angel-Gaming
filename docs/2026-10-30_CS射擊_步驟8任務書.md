## 一、目標

經營層（M4，`src/manage/`）目前每場戰隊賽＝3 個 1 對 1 對位、由 `FakeGateway` 擲骰。步驟 8 把它改成**名單對名單一場比賽**、名單人數由內容包宣告，再把攻防戰的真引擎接成第二個閘道：使用者在正式版介面開新局時可以選「攻防戰」，整季比賽由基準 Bot 2.1 依選手的角色、版本、習慣真打出來。經營核心仍然不知道賽制內容：只送名單與種子、只收勝負與比分（使用者的原則：**閘道泛化，不管人數，只接輸贏計分**）。

## 二、設計

### 2.1 閘道契約（`src/manage/gateway.ts`）

```ts
export interface PlayerSpec { readonly lineageId: string; readonly version: number; readonly config: Readonly<Record<string, number | string>>; }
export interface SideSpec { readonly players: readonly PlayerSpec[]; }   // 順序＝出賽名單順序＝隊內序號
export interface MatchRequest { readonly formatId: string; readonly a: SideSpec; readonly b: SideSpec; readonly seed: number; }
export interface MatchRound { readonly label: string; readonly winner: Winner; readonly scoreA: number; readonly scoreB: number; }  // 累計比分
export interface MatchOutcome { readonly winner: Winner; readonly rounds: readonly MatchRound[]; }
export interface MatchFormat { readonly id: string; readonly name: string; readonly rounds: number; readonly estMsPerRound: number; readonly lineupSize: number; }
export interface BattleGateway {
  readonly formats: readonly MatchFormat[];
  simulateBatch(requests: readonly MatchRequest[], onProgress?: (done: number, total: number) => void): Promise<MatchOutcome[]>;
}
```

- `config` 仍是經營層不解讀的一包：`habit`（隱藏習慣，數值）、`presetBonus`（本場可用的戰術預設加成）。
- 契約五條不變（經營層不解讀賽制、成績單只有勝負與比分、確定性、公平由賽制處理、賽制自報回合數與耗時）。`lineupSize` 由 format 自報，核心開局時檢查 `content.lineupSize === format.lineupSize`，不符就拒絕開局。

### 2.2 經營核心（`src/manage/`）

- `ContentPack` 新增 `lineupSize: number`、`slotNames: readonly string[]`（長度＝lineupSize；軍團戰暫代包 `['先鋒','中堅','大將']`，射擊包 `['1 號位','2 號位','3 號位','4 號位','5 號位']`）。`LINEUP_SIZE` 移除，所有用到的地方改讀內容包（`state.ts` 的 `publicTeamRating`、`game.ts` 的開局人數／`lineupValid`／`ensureLineups`、`commands.ts` 的 release／setLineup、`npc.ts`、`autoplayer.ts` 的 `teamEst` 寫死的 3）。
- `FixtureResult` 改成一場：`{ lineupA: PlayerId[]; lineupB: PlayerId[]; winner: TeamId | null; scoreA: number; scoreB: number; rounds: RoundResult[] }`（`scoreA／B` ＝ 最終比分，軍團戰暫代包是 1:0）。`SlotResult` 移除；`standings` 的 `slotDiff` 改 `scoreDiff`（比分差）；`view.ts` 的 `slots` 改成 `match`（雙方名單、比分、逐回合）。`SAVE_VERSION` 升 2（舊存檔作廢，`save.ts` 已有版本檢查；網頁讀到舊檔要顯示訊息並提供開新局）。
- `playMatchDay`：每場 fixture 一張請求單（`buildSide(lineupPlayers, opponentLineupPlayers)`），`STREAM.match` 的種子改成（週, fixture 序號）。
- **Elo**：以兩邊名單的平均 Elo 算期望值，名單內每個人加同一個 delta（`updateElo` 的 delta，正負對稱，所以兩隊總分守恆）；`games` 各 +1。
- **獎金**：`slotWinBonus` 改名 `roundWinBonus`，乘的是本場贏的回合數（`scoreA`）；射擊包的數值要自己定（一場 13～16 回合，總額應與軍團戰暫代包「贏 2 個對位」同一個量級）。
- **戰術預設**：`buildSide` 的 specific 預設在對方名單裡**有任何人**是該流派時生效（generic 照舊）。
- **練習賽**改成隊對隊：`Command` 的 `queueScrim` 改為 `{ type: 'queueScrim'; opponentTeamId: TeamId; games: number }`，用雙方**目前的出賽名單**（無效時照 `ensureLineups` 的規則補齊，不改存檔裡的名單）打 `games` 場，報告勝場；`ScrimReport` 改記 `opponentTeamId`。研發 `queueResearch` 維持每人一個預設。`Job` 型別跟著改。
- **自由選手與開局人數**：`newGame` 每隊 `lineupSize` 人，自由選手數仍由 `economy.freeAgentCount` 決定。

### 2.3 假閘道（`gateway-fake.ts`）

- 隊伍 power ＝ 名單每人 `power[版本−1] + habit + presetBonus` 的平均；其餘照舊（`stub-bo1` 一回合擲骰）。`formats[0].lineupSize = 3`。既有測試「強的一方勝率接近表上的值」改用 3 人名單驗。

### 2.4 真閘道：攻防戰（純函式 ＋ Node／Worker 兩種殼）

- **純函式** `src/shooter/gateway.ts`（不碰 DOM、不碰 fs）：`SHOOTER_FORMATS`（`shooter-mr12`：正式賽制、`rounds: 24`、`lineupSize: 5`、`estMsPerRound` 由量測填；`shooter-short`：測試用短賽制，`roundsPerHalf` 與 `winRounds` 用 `ShooterMatchOptions` 既有的參數縮短、加時關掉，只給 vitest）；`runGatewayMatch(request, compiledBot, opts?: { record?: boolean }): { outcome: MatchOutcome; replay?: ... }`：
  - 名單 → `derivePlayer({ role: lineageId, version, habit: 0 })`，再套**習慣與預設的屬性偏移**：`shift = clamp(round(config.habit / 15), −4, 4) + clamp(round(config.presetBonus / 15), 0, 6)`，加在 aim、reaction、awareness 上後夾 0～100，`reactionTicks` 用 `reactionTicksFor` 重算。理由：經營層的 `habit` 是 ±60 Elo 的隱藏偏移（`truePower` 用它），用固定換算而不是亂數種子，讓真實強度與球探報告方向一致；預設加成是訓練的真實成果，所以也要在真比賽裡有效。換算係數 15 來自步驟 7 報告（整隊每屬性點約 15～20 整場 Elo）。
  - 座位：A 名單 0～4、B 名單 5～9；地圖 `redrock`；種子 `request.seed`；旋鈕 `derivePlayer` 給的 `role`。
  - 成績單：`winner`（平手＝`'draw'`，加時打滿會發生）、`rounds` 每回合一筆 `{ label: '第 n 回合'／'加時 n', winner, scoreA, scoreB }`（累計比分，A 隊視角）。
  - **確定性保證**：閘道用的控制器**不做 50 ms 逾時判定**（`timedOut` 永遠 false），否則慢機器或背景分頁會得到不同結果，違反契約第 3 條。這是驅動層選項，規則與 API 不變；例外仍算「該次無指令」（同一份程式碼下是確定的）。
- **Node 殼** `src/manage/gateway-shooter.ts`：`ShooterGateway implements BattleGateway`，同步逐場跑（測試、自動玩家腳本用）。
- **Worker 殼** `src/web/manage/shooter-gateway.ts` ＋ `src/web/manage/shooter-batch-worker.ts`：Worker 池（`min(4, max(1, hardwareConcurrency − 1))`），一張請求單一個工作，回傳 `MatchOutcome`；`onProgress` 給介面顯示進度。Bot 原始碼用 `?raw` 匯入並在 Worker 內 `compileBot`（照 `src/web/shooter/worker.ts` 的做法）。
- 舊的 `estMsPerRound` 契約：量 Node 單執行緒一場的平均（步驟 7 是 6～12 秒／場，約 24 回合）。

## 五、規則

- 選手 API 1.0 與引擎 1.0.0 凍結：不改 `src/shooter/sim.ts`／`config.ts`／`api.ts`／`map.ts`；不改 `bots/`。`runner.ts` 可以加驅動層選項（例如不做逾時判定的控制器），不改既有行為的預設值。
- 經營核心不得出現任何賽制專有的字樣或分支（沒有 `'shooter'`、沒有回合數、沒有角色名）；賽制專有的東西都在閘道與內容包。
- 確定性：核心與閘道都不用 `Math.random`、`Date`；Worker 版與 Node 版同一張請求單同一結果。
- 不 push、不碰 main、不動軍團戰引擎檔案。覆蓋或刪除既有檔案（例如移除 `SlotResult`、舊存檔鍵）屬於本步驟明定的變更；此外若要刪檔先在回報裡說明。
