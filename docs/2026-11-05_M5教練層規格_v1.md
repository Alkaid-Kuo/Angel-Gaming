## 零、摘要

M5 把「模擬器參數直接端給玩家」改成「教練在經營一支隊伍」，分四批，每批都能單獨驗收：

| 批 | 內容 | 玩家多了什麼 | 拿掉什麼 |
| --- | --- | --- | --- |
| 1 | 戰術手冊＋比賽計畫＋Bot 2.8 接口 | 十個戰術各有隊伍默契與個人熟練度、排練、賽前比賽計畫（偏好星級與禁用、經濟風格）、我方每回合打了什麼戰術 | 戰術研發、戰術預設、`presetBonus` |
| 2 | 選手屬性制與訓練 | 六項屬性、上限區間（隱藏潛力）、成長階段稱號、針對單一屬性訓練 | 升版指令與費用、版本號對外 |
| 3 | 比賽個人統計 | 結果幕雙方個人數據、MVP、選手近況與賽季累計、各戰術勝率 | — |
| 4 | 即時比賽與教練暫停 | 我方比賽即時算、暫停（整場兩次＋加時每段一次）、中場免費改計畫、教練視角（不能透視）、助理教練（付費代喊）、NPC 教練 | 我方比賽先算好再播 |

不變的事：`knownView()` 仍是畫面與 NPC 唯一入口；習慣仍隱藏；球探仍有價值；引擎確定性（同請求單同結果）；視野公平（Bot 與教練都拿不到己方看不到的資訊）。

## 二、共通約定

- **型別位置**：經營核心型別在 `src/manage/types.ts`、閘道契約在 `src/manage/gateway.ts`、攻防戰專有在 `src/shooter/`、內容在 `src/manage/content-shooter.ts`。經營核心仍不解讀賽制內容：戰術代號、屬性名稱等由內容包提供，核心當字串與數字處理。
- **存檔**：每批升一號 `SAVE_VERSION`（5 → 6 → 7 → 8 → 9），舊存檔讀不了，照現有做法在標題畫面說明。
- **確定性**：所有新的成長（排練、訓練、熟練度）都是確定性公式，不擲骰；需要開局分佈的地方（初始個人熟練度、隱藏上限偏移）用既有 `rngFor(seed, STREAM.…)` 串流，新增串流不得吃到既有串流的亂數（立繪池的做法）。
- **數值**：本規格裡的數字都是**初值**，標「平衡」的由實作批次量測後回報再定，不在規格階段拍板。
- **公開／隱藏**：每批列「公開／隱藏表」。原則同 M4：已發生的事實與規格表公開；真值（習慣、真實上限、真實強度、對手熟練度）隱藏，只透過球探、戰績間接看到。
- **不動**：`bots/shooter-src/` 由 Bot 工作階段改（Bot 2.7 進行中）；經營批次只在 Bot 2.8 合併後接上真 Bot，之前用假 Bot 或現行 Bot（忽略新欄位）通過自己的驗收。

### 3.3 規則

- **執行熟練度**（送給 Bot 的隊伍值）：`eff(t) = round(0.5 × team.playbook[t] + 0.5 × 出賽五人 tactics[t] 平均)`。
- **排練**（`queueRehearse { tactic, sessions }`）：用目前出賽名單（無效時照 `effectiveLineup` 補）。每一節：
  - 隊伍默契 `+= 6 × (1 − cur/100)`（取到小數一位存，顯示整數）；
  - 出賽五人個人熟練度 `+= 8 × (1 − cur/100)`。
  - 遞減式成長，越熟越難漲；不擲骰。
  - 佔用訓練中心的每週時段（第二批與單一屬性訓練共用一個池，見 4.3）；第一批先沿用 `scrimCapacity` 的格數換算：一節＝ 1 格（平衡）。每節費用 `rehearseCost`（千元，平衡）。
- **比賽使用**：每回合我方實際打的戰術（3.6 的回合戰術標籤）隊伍默契與出賽五人個人熟練度各 `+0.5 × (1 − cur/100)`；不分勝負。
- **換人**：`sign` 成功時全隊 `playbook` 各項 ×0.9（新人要磨合）；`release` 不扣。個人熟練度本來就跟著人走，換人自然改變 `eff` 的個人半邊。
- **初值**：
  - 玩家隊伍默契：每項 20；NPC 依個性（whale／data 各項 30、youth 20、miser 15，平衡）。
  - 個人熟練度：開局以新串流 `STREAM.tactics` 每項抽 10～40，加角色傾向（突破手 rush +10、游擊 split／fake +10、錨點 stackA／stackB +10、狙擊手 ct212 +10、支援 default +10），夾 0～100。
- **比賽計畫**（`setGamePlan { plan }`）：
  - 每個陣營至少一個戰術不是 -1（否則拒絕：「T 方至少要留一個戰術」）。
  - 預設：全部 0、經濟 0。NPC 依個性產生（例：whale 偏好熟練度最高的兩個各 2 星），每週開賽前跟名單一起由 `npc.ts` 重設。
  - 計畫只影響「Bot 自己選戰術」的權重，不改屬性。

### 3.4 Bot 2.8：戰術選擇的效用分數

Bot 2.8 把 `chooseT`／`chooseCT` 的機率抽選改成 Fable 審查報告七 E 的四層，戰術手冊就是第三層的權重表：

```
score(t) = S(t)                    // 狀態分：只來自可觀察狀態
         + Wp × pref(t)            // 比賽計畫星級（0～3）
         + Wq × eff(t) / 100       // 隊伍執行熟練度
         − Wr × repeat(t)          // 本半場同戰術連用的次數（防止被讀）
         + A(t)                    // 對手適應，|A| ≤ Aₘₐₓ
```

1. **狀態分 `S(t)`**：經濟（我方 eco 時 rush／split 加分、default／fake 扣分；對方疑似 eco 時 default 扣分）、兩點最近的成敗（現有 `siteScore`）、剩餘人數與時間等，全部來自觀察資料與隊內喊話。同樣狀態永遠同樣分數。
2. **取最高分**；前兩名分差 `< ε` 時才用 `rollOf(回合數, salt)` 二選一（使用者已允許以公開回合資訊做種子的確定性雜湊當平手打破器，Bot 2.7 任務書第一節）。
3. **權重表**：`pref = -1` 的戰術直接排除（教練命令除外，3.5）。`Wp`、`Wq`、`Wr`、`ε`、`Aₘₐₓ` 放在 Bot 的 P 表，初值由 Bot 2.8 量測後提出；**目標關係**（Bot 2.8 驗收用）：
   - 3 星在狀態合理時應勝出：只給 Rush B 3 星、其他 0，非 eco 的 T 回合 Rush B 佔 ≥ 50%；
   - 狀態分能蓋過 1～2 星：我方 eco 回合，Default 2 星也不打 Default；
   - 熟練度是溫和的傾向：計畫全 0 時，`eff` 80 對 20 的戰術被選比例 ≤ 2 倍；
   - 計畫全 0、熟練度全等時，任何戰術不超過 T 回合的 40%（多樣性）。
4. **對手適應**：沿用 `adaptation.js` 的勝率加權，但改成加法項並夾在 ±`Aₘₐₓ`；少於 3 回合樣本不動。
5. **包點選擇**：`default`、`fake` 的主力／真打點、`rush`／`split` 已含包點；包點內部的路線、分組仍由 Bot 決定（現有 `siteScore`＋效用框架）。
6. **滯後**：戰術每回合在凍結時間決定一次，回合中不重選（`fake` 的「探到空點轉打」是戰術內的分支，不是重選）。

### 3.5 Bot 2.8：執行品質

`eff(t)/100` 是本回合戰術的隊伍執行品質 `q`；每位選手自己的 `tactics[t]/100` 是個人執行品質 `p`。**熟練度不改槍法**：瞄準、反應、警覺只由屬性決定；`q`、`p` 只影響團隊配合。Bot 2.8 至少接三項，每項要有可量的直接指標：

| 配合項 | `q`／`p` 低 | `q`／`p` 高 | 直接指標 |
| --- | --- | --- | --- |
| 兩組同步（split／default／fake 執行） | 第二組到位等待上限長、到位判定鬆，常各打各的 | 兩組進點時間差小 | 兩組第一人進點的時間差（秒） |
| 道具時序（進點前煙閃） | 煙落地到進點間隔長或太早、閃光炸開到第一人進點延遲大 | 閃光炸開後短時間內進點 | 閃光炸開 → 第一人進點延遲；煙落地 → 進點延遲 |
| 佈置效率 | 到待命格繞遠、停頓多（走位屬性另算） | 準時到位 | 凍結結束 → 全組到待命格的時間 |

- `q` 管隊伍層（指揮的等待門檻、喊 go 的時機），`p` 管個人層（自己跟上的延遲）。
- 係數範圍：`q` 0 → 1 時上表三個指標至少改善 25%（平衡）；不得因 `q` 低而出現 Bot 2.7 修掉的錯誤行為（例如單門排隊）。
- 不在範圍：`q` 影響的不是「戰術選不選得到」，而是「選了之後打得像不像」。

### 3.6 Bot 2.8：讀什麼、何時讀、宣告什麼

**開局（`init`）讀旋鈕**（每座位、整場不變）：

| 旋鈕 | 範圍 | 意義 | 同隊五人 |
| --- | --- | --- | --- |
| `q_<tacticId>` × 10 | 0～100 整數 | 隊伍執行熟練度 `eff` | 相同 |
| `p_<tacticId>` × 10 | 0～100 整數 | 本人個人熟練度 | 各自 |
| 既有 `role`、`awpSlot` 等 | 不變 | | |

旋鈕沒給（試玩、舊請求單）時預設 50，Bot 行為等同「中等熟練」。旋鈕說明文字要短（產物上限 256 KB）。

**每回合（凍結時間第一次決策）讀教練欄位**：引擎 API 1.2 新增 `ShooterObservation.coach: TeamOrders | null`：

```ts
// src/shooter/api.ts（API 1.1 → 1.2；引擎 1.2.0 → 1.3.0）
export interface TeamOrders {
  /** 目前生效的比賽計畫（賽前計畫，或最近一次暫停／中場改過的） */
  readonly pref: Readonly<Record<string, number>>;
  readonly economy: 0 | 1 | 2;
  /** 本回合的教練命令；沒有＝null */
  readonly call: { readonly tactic: string | null; readonly buy: 'full' | 'force' | 'eco' | null } | null;
}
```

- 只含**己方**的教練指令；對方的計畫、命令、熟練度永遠不在觀察資料裡（視野公平）。
- 整回合不變（凍結到回合結束都是同一份），不是一次性訊息，所以指揮換人時新指揮讀得到。
- `call.tactic` 是命令：該回合一定打這個戰術（不管 `pref`、狀態分），Bot 只決定包點內細節；`call.buy` 覆蓋隊內買法（`B:` 喊話）。
- `coach` 為 null（試玩、對陪練）時，Bot 照 `pref` 全 0、經濟旋鈕 `economy` 行事，等同現行行為的效用版。
- `economy` 欄位取代旋鈕 `economy`（旋鈕保留給試玩頁）。

**每回合宣告戰術**：指揮在凍結時間結束前喊一次 `K:<tacticId>`（例 `K:splitB`），回合中不再喊；CT 也喊（`K:stackA`）。這是閘道與 Bot 的約定，不是引擎規則；閘道從回放或驅動層的隊內喊話取每隊每回合第一則 `K:`，變成回合戰術標籤（3.7）。喊了不存在的代號、或沒喊，標籤記 `null`。

## 四、第二批：選手屬性制與訓練

### 4.1 資料結構

```ts
interface Player {
  // 刪：version、upgradeUntilWeek、presets
  /** 表定屬性（公開；六項 0～100 整數）：aim、reaction、awareness、aggression、discipline、movement */
  attrs: Attributes;
  /** 訓練進度（百分之一點；滿 100 進 1 點），只有三項強度屬性 */
  progress: { aim: number; reaction: number; awareness: number };
  /** 隱藏：真實上限（只有三項強度屬性；風格屬性不訓練） */
  caps: { aim: number; reaction: number; awareness: number };
  /** 隱藏：習慣（沿用，−60～60） */
  habit: number;
}
type Job = … | { kind: 'train'; id: number; teamId: TeamId; playerId: PlayerId; attr: 'aim' | 'reaction' | 'awareness'; sessions: number };
```

刪除：`Command` 的 `upgradeVersion`、`Economy.upgradeCostWeeks／upgradeWeeks`、`completeUpgrades`。`RaritySpec.maxVersion` 改名 `capVersion`（意義：上限對應到哪個舊版本的屬性）。

### 4.2 屬性、上限與隱藏習慣

- **開局**：照現在抽角色、版本（只當生成參數）、品階；`attrs = derivePlayer({ role, version, habit: 0 }).attributes`。
- **公開上限**：`capPub[k] = base[k] + growth[k] × (capVersion − 3)`（N 對應舊 v2、R v3、SR v4、SSR v5），即「角色基準＋稀有度餘裕」。
- **上限區間**（公開）：`[capPub − 2, capPub + 2]`。
- **真實上限**（隱藏）：`caps[k] = capPub[k] + off[k]`，`off` 由 `habit` 決定：`off = habitCapOffsets(habit)`，三項各 −2～+2（`habitOffsets` 同法、範圍 2、不同鹽）。再保證 `caps ≥ attrs`（開局不能已超上限）。
- **比賽中的習慣偏移**（沿用，隱藏）：閘道照舊把 `clamp(round(habit/15), −4, 4)` 加在三項強度屬性上。所以習慣管兩件事：「比賽打得比表定好或差」與「天花板在區間的哪裡」，兩者同方向（習慣好的人兩邊都偏好），球探估的是同一件事。
- **風格屬性**（侵略、紀律、走位）：開局決定、本 M5 不訓練（顯示「風格」鎖頭）。
- **怎麼看出天花板**：
  - 自己的選手：訓練收益隨「離真實上限的距離」遞減（4.3），訓練報告寫收益百分比；練到收益掉下來，玩家就推得出上限大約在哪。
  - 別隊的選手：球探報告除了現有的真實強度估值，再給一項強度屬性的上限估計區間（寬 ±1，隨機選一項，種子決定）。

### 4.3 訓練

- `queueTrain { playerId, attr, sessions }`，`attr` 只能是三項強度屬性。
- **每週時段**：訓練中心等級決定，排練與訓練共用：`trainingSlots = [8, 14, 22]`（平衡）；每名選手每週最多 3 節（不能全壓一人）。練習賽仍用 `scrimCapacity`（那是引擎算力）。
- **每節收益**（百分之一點）：`gain = round(120 × clamp((caps − cur) / 6, 0, 1))`，最低 20 直到碰上限、碰上限為 0。即離上限 6 點以上每節 1.2 點，最後 6 點線性遞減。不擲骰。
- **費用**：每節 `trainCost`（千元，平衡）；訓練與排練成為主要支出，取代升版費。
- **報告**：「Nyx 瞄準 58 → 60（本週 3 節，收益 100%／100%／67%）」；收益百分比＝本節 gain ÷ 120。
- 練習時段當週排、推進時結算（同現有 jobs）。

### 4.4 成長階段（稱號）

- 強度和 `S = aim + reaction + awareness`；角色門檻 `T(v) = Σbase + Σgrowth × (v − 3)`。
- `stage = max{ v ∈ 1..5 : S ≥ T(v) }`（S 低於 T(1) 也算 1）。稱號：1 新秀、2 正選、3 主力、4 明星、5 傳奇。
- 只作顯示與 `publicPrior` 起點；不能購買、不影響薪資（M5 薪資在簽約時定、季中不變；續約留到合約系統）。
- 品階文案：「SR：上限約到明星」。

### 4.5 真實強度與 NPC

- `truePower`（隱藏，給球探、賠率、內容層）：小數版本 `vf = 3 + (S − T(3)) / Σgrowth`，在 `SHOOTER_POWER[role]` 上線性內插（夾 1～5），再加 `habit`。
- NPC：簽約估值用公開屬性＋品階（`npcEloBonus` 沿用）；NPC 也排訓練（依個性分配時段，例 data 練離上限最遠的、youth 只練新秀），經同一套指令。
- `PlayerSpec.version` 保留（填 `stage`，只給舊介面顯示），閘道改從 `config` 取屬性。

### 4.6 閘道契約（第二批）

## 六、第四批：即時比賽與教練暫停

### 6.1 流程

- 推進一週時：其他比賽照舊批次算；**我方比賽**賽前三選一：
  - 「以教練身分看」：即時算、己方視角（6.6）、可暫停下指令。
  - 「一般觀戰」：正常全知觀戰（和現在一樣），不能下指令；我方由助理教練（有請時）或照比賽計畫打，和跳過的結果相同。
  - 「跳過」：批次算（照計畫＋助理教練規則）。
- 教練身分中途可以轉成一般觀戰（之後不能再下指令、助理教練從下一回合接手），反過來不行：看過全知畫面就不能再當教練。
- 核心 API：`advance()` 分兩段——`beginMatchDay()` 回傳我方賽程的即時票（請求單，不含隱藏資料以外的東西照現有 `watchTicket` 規則經 store 轉交），即時頁跑完回傳 `{ calls, outcome }`，`finishMatchDay(live)` 寫入結果、續推其餘流程。沒有我方比賽（輪空）就直接走原流程。
- 即時頁中途關閉：視同跳過，該場從頭以批次重算（已喊的暫停作廢）。不保存半場進度（規格 v1 簡化）。

### 6.2 教練指令與請求單

```ts
// src/manage/gateway.ts
export interface CoachEvent {
  /** 從這回合的凍結時間起生效 */
  readonly round: number;
  readonly side: 'a' | 'b';
  readonly kind: 'timeout' | 'halftime';
  /** 改過的比賽計畫（沒改＝null） */
  readonly plan: { readonly pref: Readonly<Record<string, number>>; readonly economy: 0 | 1 | 2 } | null;
  /** 本回合命令 */
  readonly call: { readonly tactic: string | null; readonly buy: 'full' | 'force' | 'eco' | null } | null;
  /** 誰喊的：玩家、助理教練、NPC 教練（只供顯示） */
  readonly by: 'human' | 'assistant' | 'npc';
}
export interface MatchRequest {
  // …既有
  /** 玩家在即時比賽喊的指令（依回合排序） */
  readonly calls?: readonly CoachEvent[];
  /** 哪一方由 AI 教練代喊（NPC 教練或助理教練） */
  readonly coachAi?: { readonly a: boolean; readonly b: boolean };
}
export interface MatchOutcome {
  // …既有
  /** 雙方所有生效的指令（含 AI 教練喊的），回放與結果幕顯示用 */
  readonly calls?: readonly CoachEvent[];
}
```

- **確定性**：指令在該回合凍結時間的**第一個 tick、任何 Bot 決策之前**寫進 `obs.coach`。所以「請求單＋玩家指令」重跑，與當時即時打的那場完全相同；AI 教練的指令在驅動層由公開狀態算出，重跑也相同。
- **次數**：每方正規兩次 `timeout`，加時每段 +1；`halftime` 不扣次數、每個換邊點一次。超過次數的事件閘道丟例外（核心送出前先檢查）。
- **生效範圍**：`call` 只管那一回合；`plan` 從那回合起一直生效到下次修改。

### 6.3 AI 教練（NPC 教練與助理教練同一套）

在驅動層、每回合凍結第一個 tick 前執行，**只讀己方可知的資訊**：比分、每回合勝方與結束原因、己方每回合戰術標籤與勝負、己方平均金錢、剩餘暫停次數、己方 `eff`。規則（初值，平衡）：

1. 喊暫停的條件（擇一）：連輸 3 回合；對方到賽點且我方落後；中場換邊（免費，只改計畫）。
2. 命令：在 `pref ≥ 0` 的戰術中選 `eff × (1 + 0.5 × 本場該戰術勝率 − 0.5 × 本場該戰術連敗次數)` 最高者；同分以 `rollOf` 打破。
3. 經濟：己方平均金錢 < 2000 且不是半場最後一回合 → `eco`；否則不下命令。
4. 中場改計畫：把本場打過且輸多於贏的戰術降一星，贏多的升一星（夾 0～3）。

- NPC 隊：whale、data 個性「有教練」（`coachAi` true），youth、miser 依現金 ≥ 門檻才請（平衡）。
- 玩家：助理教練是設施型支出（`hireAssistant`／`fireAssistant`，週薪 `assistantSalary`，平衡）；有請時，我方「跳過」的比賽 `coachAi.玩家方 = true`；玩家自己看時由玩家喊，助理教練不代喊。

### 6.4 Bot 端

Bot 2.8 已讀 `obs.coach`（第一批），第四批不再改 Bot：`call.tactic` 命令、`plan` 變動都是同一個欄位。驗收時確認「凍結時間第一次決策讀到的 `coach` 就是新指令」。

### 6.5 即時頁（`web/shooter.html#watch` 的教練模式）

- 經營頁開即時票（同現有嵌入觀戰 `EMBED`），即時頁用 `gatewayDriverOptions` 建驅動逐 tick 推進（現有觀戰 Worker 的路徑），差別是不預知結果、可暫停。
- **暫停鍵**：「暫停（剩 2）」，按下後本回合照打，驅動跑到下一回合凍結第一個 tick 前停住，跳出教練面板。
- **教練面板**：下一回合戰術（陣營對應的戰術清單＋「交給選手」）、經濟（全買／強起／存錢／交給選手）、修改比賽計畫（星級、經濟風格）。沒有倒數（單人遊戲，模擬已停）。按「繼續」送出事件、恢復推進。
- **中場**：換邊時自動停一次，面板只有「修改比賽計畫」，可直接繼續。
- 速度控制沿用；**不能往後跳**（結果還沒算）；可以往回看已打完的回合（只看己方視角，見 6.6）。
- 比賽結束：結果幕顯示雙方的暫停與命令時間軸（對方的這時才公開）。

### 6.6 教練視角：不能透視（視野公平）

即時看我方比賽時，畫面只呈現己方隊伍知道的事：

| 呈現 | 允許 | 不允許 |
| --- | --- | --- |
| 己方五人 | 位置、血量、武器、道具、金錢、視錐 | — |
| 敵方 | 己方任一人觀察資料裡的敵人（`obs.enemies` 聯集）與雷達接觸；計分板的存活數與擊殺紀錄 | 視野外的位置、血量、武器、金錢、道具 |
| 地圖 | 己方五人視野聯集的迷霧（擴充 `render.ts` 的單人視錐迷霧為隊伍聯集） | 全圖無迷霧 |
| 對方指令 | — | 對方的暫停內容、計畫、命令（結束後才公開） |
| 聲音 | 己方選手聽到的聲音方向（可選，用己方觀察資料的 `sounds`） | 全圖聲音 |

- 資料來源：即時 Worker 本來就有每個座位的觀察資料；教練模式只送己方五個座位觀察資料的聯集給畫面，**不送 FullState**（避免畫面層誤用）。
- 一般觀戰（含我方比賽選「一般觀戰」、我方沒參與的比賽、比賽結束後的回放）：維持現在的全知觀戰，所有觀戰功能照常，只是沒有暫停鍵與教練面板。
- 往回看已打完的回合時也維持己方視角，直到比賽結束。

### 6.7 公開／隱藏

| 資料 | 公開時機 |
| --- | --- |
| 我方指令 | 隨時（自己的） |
| 對方指令 | 比賽結束後（結果幕、回放） |
| 對方位置等 | 比賽中只限己方看得到的；結束後回放全知 |
| AI 教練的規則 | 公開（說明頁），NPC 是否請教練由個性決定、不顯示 |

### 6.8 驗收（第四批）

1. 確定性：即時打一場（腳本模擬在第 3、8 回合暫停、各喊不同命令、中場改計畫），與「請求單＋指令」批次重跑的成績單、終局雜湊、回合戰術標籤完全相同。
2. 命令生效：被喊的回合，回合戰術標籤 ＝ 命令戰術（100%）；`buy` 命令生效（該回合購買結果符合）。
3. 次數與時機：第三次正規暫停被拒；回合中按暫停在下一回合凍結才停；中場不扣次數。
4. 視野公平：教練模式畫面收到的資料，對每一 tick 檢查「敵方出現 ⇒ 在某名己方選手的觀察資料裡」；對方指令在比賽結束前不在畫面資料裡。
5. AI 教練：只讀 6.3 列的輸入（以型別限制輸入物件）；同一場重跑同一組指令；NPC 隊有／沒有教練各跑 200 場，勝率差回報（預期小，平衡）。
6. 效能：即時推進在一般機器 1 倍速不卡（基準 Bot 決策耗時已量過，閒置下無虞）；暫停時 CPU 閒置。
7. 中途關閉：該場以批次重算，結果有效、存檔一致。
8. 一般觀戰：我方比賽選一般觀戰時全知畫面正常、沒有暫停鍵；結果與跳過相同（同請求單）。教練轉一般觀戰後不能再下指令；一般觀戰不能轉教練。

## 七、Bot 2.8 任務摘要（給 Bot 工作階段）

前提：Bot 2.7 全部合併（尤其批 3 的效用框架）、M5 經營批次 1a 合併（引擎 API 1.2 的 `coach` 欄位）。

1. 宣告旋鈕 `q_<tacticId>`、`p_<tacticId>`（各 10 個，0～100，預設 50）。
2. `chooseT`／`chooseCT` 改效用選擇（3.4），P 表放權重；`pref -1` 排除；`call.tactic` 強制；`call.buy` 覆蓋買法；`coach.economy` 取代旋鈕 `economy`。
3. 執行品質 `q`／`p` 接三項配合（3.5），各有直接指標。
4. 指揮每回合喊 `K:<tacticId>`（3.6）。
5. 視野公平：Bot 只讀自己的旋鈕與 `obs.coach`；不讀、也拿不到對方的任何指令。
6. 驗收：3.10 第 5、6 條；產物 ≤ 256 KB；試玩頁基準 v1～v5 不受影響。
7. 不做：教練 AI（在驅動層，不在 Bot）；統計（閘道算）。

## 九、待審重點（給審查的 Fable 工作階段）

1. 3.4 的目標關係是否足以約束 Bot 2.8，又不綁死實作。
2. `eff` 用五五合算，與 `sign` 九折，是否讓「換人」的代價夠明確。
3. 4.2 習慣同時管比賽偏移與上限位置，是否讓球探估值一致、又不讓玩家太快推出真值。
4. 6.1 即時頁中途關閉以批次重算，是否有被濫用的空間（看到劣勢就關掉重來）——v1 的答案：重算用同一請求單、沒有玩家指令，結果是「沒有教練的版本」，不會比較好也不會隨機變化；但仍請審查確認。
5. 6.6 的視野聯集是否涵蓋所有資訊管道（擊殺提示、計分板金錢等）。
