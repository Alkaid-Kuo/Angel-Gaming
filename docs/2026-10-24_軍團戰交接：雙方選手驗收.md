## 二、驗收清單（建議順序）

1. **受保護檔案沒被改**：把 `out/legion-pack.zip` 解到 scratchpad，和各資料夾逐檔比對（`src/`、`bots/`、README、spec、datasheet、match.ts、trace.ts、package.json、node_modules/acorn）。
2. **合法性**：在原版包內跑 `node match.ts --check <選手>`；檔案 ≤ 200 KB；decide 上限 50 ms（批次模式超過就整場閒置），在有負載時也要量最長耗時。
3. **獨立重跑驗收**：用**他們沒看過的新種子**（例如 5001～5050），原版包的 `match.ts`，兩模式、三陪練、交換座位。與他們自報的數字比對；他們的逐場紀錄要抽查幾場用 `match.ts` 重現（引擎是確定性的，同種子同座位結果應一致）。
4. **交叉對戰**：將軍、元帥（新）、元帥 v1、統帥、舊統帥互打，兩模式、每組至少 40 場（20 場的雜訊約 ±2 場，曾經誤判過好幾次）。
5. **出處審查**：
   - 跟陪練比對（禁止複製）：陪練共用的 `LegionBase` 與輔助函式名稱，例如 `scoutReact`、`safeStep`、`landBehind`、`spearReact`、`nearestFoe`、`remembered`、`lastSeenAt`、`TR = { plain: 0, road: 1, ...}`。元帥 v1 檔頭自稱「共用兵種輔助函式源自開發包」——第二輪的提示詞已禁止。
   - 元帥（GPT）也要跟統帥比對（GPT 第一輪看過統帥）。
6. **規則遵守**：開局資料（`LegionInitData`）沒有對手名稱與種子，所以查的是：有沒有利用已知資訊外洩（見三-2）、有沒有讀引擎內部（沙盒應擋住）、依觀察到的編成調整是合法的。
7. **流程誠信**：用 git 歷史與時間戳確認驗收種子沒有參與調校、沒有只重跑失敗場、驗收程式 SHA256 與交付檔一致。
8. **觀戰**：要在網頁看，照 1bdb2a1 的做法加：`bots/legion-<名>.js`、`src/web/legion/{protocol.ts BotKey, main.ts BOT_KEYS, worker.ts import 與 compiled}`、`web/legion.html` 兩個下拉選單、`eslint.config.js` 與 `tsconfig.json` 排除該檔，然後 `npm run build:web`（8000 埠的區網伺服器提供的是 `dist-web`，不必重啟）。

## 三、已知問題與設計疑點

1. **時間到比戰果，鼓勵「先咬一口再龜縮」**：元帥 v1 殲滅戰用 8 團弓兵在高地擺火線不出擊，開場吃掉我方斥候（戰果 21:0）後固守，統帥 0:20。統帥修掉送分後變 0 勝 10 敗 10 和（剩下的敗場是戰果 0:1 的小差距），但仍攻不破弓兵要塞。這是規則設計問題，也是統帥的弱點（「戰果」怎麼判定是使用者先前決定的，聯賽平手的處理延後再訂）。
2. **資訊外洩**（規格書照實寫了，尚未修引擎）：軍團 id 先編藍方再編紅方，紅方從自己的第一個 id 就知道藍方共幾團（含後備）；旗點的佔領進度與佔領方不受迷霧限制。
3. **伏擊陪練偏弱**：空白範本在佔點對它 6 戰全勝，「贏三隻陪練」的門檻在伏擊這組偏低。
4. **規格書 17.2**「不得嘗試繞過沙盒，違反者不予計分」是建包時加的，使用者還沒確認要不要保留。
5. **舊草案與引擎不一致的 11 處**（規格書照引擎寫）：河流不擋視線（數值總表已更正）；上下坡只看高低不論差幾階；高度視野加成是 +2 格 ×（高度 − 1）；切入轉向每秒 40°；衝勁不影響速度只影響撞擊；撞擊公式另乘老兵、相剋、剩餘衝勁與衝刺高度加成（下坡算兩次）、騎兵撞人往側推 0.4 格；齊射中下移動類指令會取消齊射；隱蔽偵測用「中心距 − 雙方半徑」；時間限制只有批次模式的 50 ms 硬上限（無窮迴圈中斷不了）、init／deploy 各 1000 ms；架好的盾牆與槍林所有方向都不參與推擠；齊射打切入中士兵的命中率 25/60。
