# CS 射擊 Bot 審查報告 — Astra

日期：2026-11-05。範圍：`34e3708..feb0e70`，實際工作樹 HEAD `cc686075`。本輪只讀生產程式，未修改 Bot、引擎、情境、測試或提交程式碼；變體與重現工具放在 `out/astra-review/`。

## 1. 結論

**現有數據確認指定種子上的 T 勝率下降，但不足以證明「2.6.3 整體變弱」，也不能將下降歸因於單一開關。** 鏡像衡量攻守平衡，兩方同時換版本；它不等同於對固定對手的強度。B2 單獨關閉在 v5 有改善、在 v3 幾乎沒有；B3 與進點記憶單獨關閉都未穩定回復舊版。這不是「功能沒有影響」的證明。

審查找到兩個容易使歸因失真的遺漏：閃光宣告清除半徑由 4 格改為 6 格；`flashRelease=false` 也未完全恢復舊邊界。因此「三項全關」不能直接當作 2.6.2。相關補測見下節。

**可確認的程式問題與勝率歸因分開處理。** 已獨立重現：撿槍覆蓋拆包目標、同點掉落物阻止撿槍、進點記憶混用 A/B、第一顆閃光遮蔽第二顆的避閃判斷、加時首局被當作賽點、同位置兩次投擲被去重成一顆、閃光候選快取不隨敵情失效、繞後者仍算在原進點組人數中。

**最值得先做的瘦身是建置階段移除型別註解。** 產生檔由 **260,058 → 227,832 bytes**，省 **32,226 bytes**，距 262,144 上限剩 **34,312 bytes**。token 一致；兩個種子的比分、逐場結果與最終狀態雜湊一致。這是本輪已量出的數字，不是估計。型別檢查須改為檢查有 JSDoc 的來源模組，不能把刪型別與放棄型別檢查綁在一起。

### 2.3 未被三個開關還原的差異

`tactics.js:704` 收到 `E:flash` 後，原本只刪除 4 格內的 claim，現在刪除 6 格內的 claim／seen。即使 `flashSeeDodge=false`，擴大的 claim 清除半徑仍生效；另一顆尚未出手的宣告也可能一起被刪。

`tactics.js:2886` 的 `flashRelease=false` 將 release 設成 −2，卻使用 `t < pop + 2`；舊版是先取閃光、後以 `t <= pop + 2` 判定。恰在 `pop+2` 的決策因此不同。這個極小差異也能在確定性對局中延伸為不同的後續比賽，不能忽略後把全部差額歸給清除半徑。

精確還原版在 v3、v5 各 80 筆兩側記錄的比分、陣營回合、結果、理由及行為計數，均與 2.6.2 逐筆相同（`verify-restored.mjs`／`factorial-and-isolation.json`）。在這批樣本中，還原已辨識的有效差異足以恢復舊版；不代表已確定各差異的平均強度影響。只還原半徑或等號都會改變部分對局；`release-boundary.mjs` 也直接重現 pop+2 時舊版 urgent/hard=true、關開關版=false。

**歸因結論**：各項會改變確定性軌跡，且有組合效應；已定位可重現的具體漏洞，但目前沒有足夠證據將完整 200 種子的淨下降分配給單一原因。先修已證實的錯誤，再用固定對手及保留種子驗收，比從小差額回推唯一根因可靠。這是本輪尚未解決的統計歸因限制，不能寫成已排除所有功能。

### 2.4 友閃數字應如何解讀

原評測器的 `flashTeamPct` 實際是 **隊友致盲 tick／敵方致盲 tick**，不是「隊友占全部」，也不是人次。v3 的 17.484% → 13.550%、v5 的 12.941% → 10.915%，與 `m6.ts` 的「大於 9 tick 的友閃事件數」不能直接互相驗證。

任務書的前 40 場 11 → 13、100 場 36 → 63 都是增加，沒有方向相反。另核對既有 `m-n1.json/.txt` 的 40 種子資料：關提前放行後，友閃為 23 人次，現版 13、舊版 11；三者回合數分別 481、436、509，T 閃光數 712、644、774。關閉 B2 沒有在這批資料裡降低友閃。這不否定下節多閃光遮蔽的漏洞，但不足以把整場友閃增量全歸因於 B2。

「閃光後 3 秒擊殺」是時間上的共現，還會受投擲數、交戰時機與回合長度影響；不能單憑 0.294 → 0.347 認定閃光戰術效率提高。下一輪應逐顆連結投擲者、預測／真實爆點、接收喊話時間、避閃命令生效時間與受害者，並同報每 100 顆／每 100 回合的友閃與擊殺。

## 3. 問題清單（依嚴重度）

以下行號指 `feb0e70` 的來源檔；除另註外均位於 `bots/shooter-src/`。P1 表示會直接破壞關鍵任務或不符合任務書明文規範；P2 是應修正的戰術／狀態錯誤；P3 是效能、維護或驗收改善。bytes 的「約 0」表示不是瘦身項目，修正通常會略增加程式。重現腳本只在 `out/astra-review/`，沒有加入正式測試。

### P1-1：撿槍覆蓋期限任務，之後反而鎖定錯誤目標

- **位置**：`tactics.js:512–519,1082–1110`；`mission.js:48–63`。
- **問題／證據**：先產生拆包／撿彈／下包目標，再呼叫 `grab`，最後才 `mission.assess`。`grab` 檢查 `out.commit` 時尚未計算，走向目標時 `objective` 也仍為 false。`extra-counterexamples.mjs` 給 CT 拆包任務、剩 7 秒、敵方已全滅及腳邊較好槍：結果仍是 `task=defuse`，`goal` 卻變成槍的位置，且 `commit=true`。期限與避火也以被換掉的座標計算。
- **建議**：先確立任務與 deadline；撿槍只能提出可中斷的候選，不能覆蓋 critical 的任務。或讓 `grab` 明確排除正在趕往期限目標的任務，再評估有餘裕的順路拾取。不要僅在最後重算 commit。
- **行為／大小**：會；減少趕拆／趕下包時繞去撿槍。省約 0 bytes。

### P1-2：自製概率抽樣不符合任務書指定的亂數來源

- **位置**：`tactics.js:42–46,1656,2486,3280,3362`；`git blame` 顯示 helper 於 `dc05eef`（2.5 第二批）加入。
- **問題／證據**：`rollOf(round,salt)` 自行以整數混合產生值，用於繞後概率、探點與守位抽選，沒有呼叫 `helpers.random()`。它是公開回合資訊的確定性雜湊，**未讀取隱藏狀態，也不會造成不確定性**；但其「固定亂數」與概率用途不符合本任務書「亂數只能用 helpers」的明文要求。嚴重度依任務書的規則要求列 P1，不能將它描述成已證實作弊或引擎拒收。
- **建議**：若該限制確實包括這類共享雜湊抽選，改由指揮透過 helpers 抽樣後，用既有通訊流程廣播決策／抽樣值。不要讓每名 Bot 各自呼叫其 random 取代共享結果，否則分工可能不同步。若專案原意允許公開資料的固定排程，應明文記錄這個例外，不能默認全部符合。
- **行為／大小**：改用 helpers 會改變抽樣序列與行為；需驗證全隊一致及可重現。省約 0 bytes，通訊與狀態可能增加程式。

### P2-1：進過 B 被當作已突破 A

- **位置**：`tactics.js:259,390,572,1813–1824`。
- **問題／證據**：`wentIn` 只有隊員 id，沒有 site。`counterexamples.mjs` 讓兩名隊友進過 B，A 無人進入，AWP 等 A 的結果仍由 true 變 false。reset 會清空，故不是跨回合殘留；default/fake 轉點特別容易觸發語意錯置。
- **建議**：至少按 site 記錄；是否按執行階段重置需明定，確保先前佯攻不等同於目前主攻的突破。保留「進過同一點後退到矩形外也算」的合理功能。
- **行為／大小**：會；修正錯誤提前進點，不能保證淨勝率增加。省約 0 bytes。

### P2-2：第一顆進入放行窗，遮住仍須躲的第二顆閃光

- **位置**：`tactics.js:2881–2886,2922`。
- **問題／證據**：先 `.find` 第一顆看得到的閃光，才套用 release。第一顆剩 3 tick、第二顆剩 30 tick 的重現中，只有第二顆時 `urgent=true`，同時有第一顆卻變成 false。後面的 pending 可能叫停，但不會補上背身／躲藏方向。自己的 away 優先也應納入多顆威脅測試。
- **建議**：先篩出在命令生效時仍有威脅的所有閃光，再決定可同時安全的移動／視角；最低限度應將 release 條件放入尋找候選的條件，而不是先找到過期候選才放棄整次避閃。明定等號與負 release 邊界。
- **行為／大小**：會；改善重疊閃光防護，可能延遲進點。省約 0 bytes。這是已重現的漏洞，不等於已解釋整場友閃增量。

### P2-3：同位置掉落物使撿槍永久卡住

- **位置**：`tactics.js:1112–1119`；引擎對照 `src/shooter/sim.ts:1200–1217`（本輪只讀）。
- **問題／證據**：`near` 用所有物品的 `<=` 距離阻止 pickup。槍與 kit 同座標時永遠等距，走近不會解開；重現為有 kit 時無 pickup、移除 kit 後立即 pickup。引擎會先排除不適用的 bomb／kit，再以嚴格 `<` 選第一個，與 Bot 的模擬規則不同。CT 死亡、贈槍者換掉原槍均可能形成同點物品。
- **建議**：依公開規則模擬「下一個實際會撿到什麼」，處理同點物品順序，保留反應延遲冷卻，觀察負載改變後再決定下一次 pickup，避免舊槍反覆撿回。
- **行為／大小**：會；讓發槍與地面升級可靠。省約 0 bytes。

### P2-4：加時第一局就判定沒有下一回合可保槍

- **位置**：`economy.js:139–143`；呼叫 `tactics.js:2669`。
- **問題／證據**：半場長度有分加時，對手賽點卻固定用 regulation `winRounds-1`。MR12 的 12:12、MR6 的 6:6，在加時第一局仍回傳 true。既有測試只驗一般賽點及半場末局，沒覆蓋加時。
- **建議**：依公開賽制與目前加時輪次推導當輪獲勝門檻；同時檢查經濟決策中同類的 regulation 門檻。測試一般賽點、加時首局、加時真正賽點、加時半場末局。
- **行為／大小**：會；恢復加時非賽點的保槍選項。省約 0 bytes。

### P2-5：閃光以空間距離去重，兩次投擲被當作一顆

- **位置**：`tactics.js:1554–1575`，以及 `704–708,1580–1582`。
- **問題／證據**：兩次真實 `flashSpots` 位於同一落點、距今 30／27 tick，`flashNext` 仍回傳 `{ok:true, second:true}`，可放第三顆。同一投擲的飛行位置與宣告落點超過去重距離時，反過來又可能重複計數。半徑 4→6 的 claim 清除同樣缺乏投擲身份。
- **建議**：用投擲者＋投擲序號／時間識別事件，分開「宣告、已出手、已爆」狀態；可見拋體只能保守關聯，不能拿座標相同直接當成同一顆。統一資料層後，`flashDone`／`flashNext`／`flashTaken` 各自保留不同政策，不要直接合併其 8 格與入口範圍等語意。
- **行為／大小**：會；更準確控制第二顆與避免疊閃。省約 0 bytes；新資料結構可能略增大小。

### P2-6：煙的歷史紀錄被當成當下有效煙霧

- **位置**：`tactics.js:540,1391–1402,1977–2009` 及接收煙事件的分支。
- **問題／證據**：`smokes` 僅存座標，每回合清空，沒有到期時間。B3 選火時要求歷史煙座標不在火附近；煙散後同處再燃燒，仍會把新火排除。閃光候選評分也可能繼續認為該線被煙遮住。這是條件與狀態生命週期的直接靜態證據；本輪沒有量出此個案的整場頻率。
- **建議**：分開「本回合曾經投擲，用於避免重複戰術」與「目前有效效果，用於可視／滅火」。後者讀觀察到的效果或帶期限的可信事件。`onWay` 的 me→包點中心直線不是導航路線，應在實際即將走過的路段判阻塞；保留封槍線煙或滅火須明列優先級。
- **行為／大小**：會；允許再燃時處理新火，避免為不在路上的火花掉關鍵煙。省約 0 bytes。**「B3 因挪用封架點煙導致整體變弱」仍是未證實推測**，單關對照未支持將其列為主因。

### P2-7：閃光候選快取沒有敵情失效條件

- **位置**：`tactics.js:1973–2016`。
- **問題／證據**：key 只有 site／portal／煙數，評分卻讀 `cleared`、`threats`、聲音 sectors。重現中增加新聲音並前進 30 tick，候選計算仍只讀過一次 threats；手動清 key 後才讀第二次。每回合 reset 不能解決同回合新敵情。
- **建議**：快取地圖候選與 LOS；每次使用時重評少量候選的動態分數，或以敵情版本／短 TTL 失效。不要以每 tick 全圖掃描替代現有快取。
- **行為／大小**：會；閃光可回應新接觸點。省約 0 bytes。

### P2-8：繞後者離隊後，原組仍以兩人分工

- **位置**：`tactics.js:1178–1198,1261–1277,1586–1605,1648–1663`。
- **問題／證據**：`lurkOf` 只讓本人的 tGoal 走繞後路線，原 group／memberIndex／groupSize 不排除他。重現 round 6、default A、id 3 已取得繞後路線，原組仍回報成員 `[3,4]`、size 2。剩下的人仍按雙人組分配閃光順序、煙霧手與待命格。
- **建議**：區分穩定路線分組與當前參與該入口的成員，明定繞後退出／重新加入時機。各隊員應能用同一公開資訊算出相同結果，必要時廣播角色任務；不要以隊友不可見道具資料補救。
- **行為／大小**：會；改善單人留組時的道具接手與進點排序。省約 0 bytes。

### P3-1：保槍 Dijkstra 可限制到實際候選距離

- **位置**：`tactics.js:2775–2796`；`base.js:720–742`。
- **問題／證據**：每 2 秒重算整張圖，卻只使用成本 ≤400 的節點。既有 dijkstra 已有 limit 參數。重現位置全圖可達 6,404 格，限制 400 後 1,178 格；所有原距離 ≤400 的數值完全相等。這是可減少工作量的證據，尚不是正式沙箱耗時改善的測量。
- **建議**：使用 `dijkstra(g,[start],400)`，再視需要避免全圖候選迴圈。Dijkstra 成本是直走 10、斜走 14，400 不是世界座標 400，也不是保證 40 個離散步。
- **行為／大小**：只加 limit 的修正預期不變；需相同種子逐場／雜湊驗證。**增加約 5 bytes**，不是瘦身項目。

### P3-2：退役開關與寫入後未使用的診斷狀態仍佔選手檔

- **位置**：`base.js:163,207–227,306–320`；`tactics.js:181–188,320–328,347,2322–2325`；`utility.js:37,171`。
- **問題／證據**：`hits` 的歷史與 `lastAttack` 鏈只維護紀錄，未用於策略；`planStats` 未見測試／量測工具消費；`Utility.throws` 只累加。`siteScore` 與 `lastKind` 的其他用途不能一起刪。預設 false 分支與處理表見第 6 節。
- **建議**：將研究用診斷保留在外部量測或建置選項，不打包到正式選手；退役分支由 Git 歷史保留。刪除後跑固定種子的行為等價檢查。
- **行為／大小**：預設配置下預期不變；診斷欄位與可切開關的研究能力會改變。診斷狀態估省 0.4–0.9 KB，未實作前不能加進已證實節省量。

## 4. 規則覆蓋、狀態與效能審查

### 4.1 最終命令的覆蓋次序

`Tactics.update`：`tGoal/ctGoal → grab → mission.avoidFire → mission.assess → anyNade → overlay → cooperation.apply → lineCheck → utility.step`。後兩者受 wish／acted 等條件限制；commit、urgent、尚未爆的隊友閃光會取消新的道具 wish。

`baseline` 的移動決策仍先處理戰鬥避險，再是 `tac.escape`、未接戰時的 commit、戰鬥 stop／point，才到戰術 stop 與一般導航。瞄準也有 engaged、urgent、hard 的優先規則。所以「後呼叫的函式一定完全蓋過前者」不正確；應同時追 `goal/stop/look/urgent/hard/escape/commit/task`，以及延遲生效的命令。

本輪確認 P1-1 的目標／任務不一致與 P2-2 的多閃光遮蔽；沒有足夠證據把 `lineCheck`、探點或保槍整條鏈統稱為互相衝突。修正宜先集中任務保護與威脅選擇，避免大幅重排整個流程後無法歸因。

### 4.2 reset、協定、單位、公平性

- 新增 `wentIn`、claim、gift、save 等主要回合狀態有 reset；未發現可證明的跨回合殘留致命錯誤。`coop.acted` 雖不在 reset 清，但 apply 使用前會重設；`util.lastLook` 的使用受已清除的瞄準狀態限制，不能只因 constructor 有、reset 沒有就報 bug。
- `probeSpots`、`deepSpots`、`flankSpot` 是不變地圖的幾何候選，跨回合留快取合理；若測試動態改 P 或重用 Bot 換地圖則須重建。真正的動態失效問題是 P2-7。
- `readChat:659–708` 對第一個計畫、B 買法即時處理；後續事件依 eventDelay 排隊，游擊對 P 變更另有即時例外。未發現所有 E 被錯當即時事件；投擲身份關聯與延遲後仍有效的篩選要另補測。
- 本輪未發現生產 Bot 使用 `Math.random`／`Date`、硬編碼地圖 id／戰術座標，或讀取觀察外的敵方真實位置。地圖幾何來自 init；敵情來自觀察、記憶與喊話。測試／量測工具讀完整引擎狀態不等於 Bot 越權。但 `rollOf` 的自製概率抽樣與指定來源的衝突已另列 P1-2，不能宣稱全部符合任務書。
- 未發現可確認的格／世界座標全面混用；特別注意 dijkstra 成本、UNIT=1000、30 tick/s 與事件座標編碼不是同一單位。

### 4.3 效能證據的邊界

已讀並核對既有 `out/bot6/prof2.ts` 與 `prof2-idle.txt`。來源模組直接執行的兩場 raw 側寫：v3 77,100 次決策、平均約 0.05 ms、最大 9.4 ms、3 次超過 5 ms；v5 96,040 次、平均約 0.06 ms、最大 8.5 ms、3 次超過 5 ms。沒有超過 50 ms，**但兩場且非正式沙箱，不能作為限時全面合格證明**；init 1 秒限制也未由此驗證。

函式側寫中，主要累計成本在 `Judgment.approach`、感知掃描／危險圖、A*；單次 `flashPoint` 約 1.4 ms、`deepSpots` 約 1.1 ms，`postPlant` 的一次 6 ms 主要來自 evacuation 約 5.6 ms。資料支持先限縮已確定冗餘搜尋、分離靜態幾何與動態評分，不支持只因 flashPoint 程式長就重寫。saveSpot 未進累計前列也不能證明稀有保槍情境沒有尖峰。

後續效能驗收應在機器空閒時，用正式沙箱、兩張圖、v3/v5、包含首次決策與殘局的種子，分開記 init、p95/p99/max 與 >5/>50 ms 次數；不能拿 `--no-limits` 的勝率當限時驗收。

## 7. 建議執行與驗收順序

1. **先做可核對的建置瘦身**：只刪產物 JSDoc／無用註解，來源保留型別；調整 typecheck 輸入並維持 build --check。驗收實際 bytes、token、同種子逐場比分與正式回放雜湊一致。與任何行為修正分開提交。
2. **修任務目標與拾取**：先加入 P1-1、同點槍＋kit／兩槍／不適用物品、反應延遲的 regression，再改任務仲裁。驗收關鍵拆包／下包期限與發槍成功，不只看有沒有 pickup 指令。
3. **確認共享抽樣規範並修獨立狀態問題**：先落實 P1-2 的來源要求或明文例外；加時判定、按點進入記憶、繞後參與名單分批修。每批都保留既有合理行為的正例與本輪反例。這些會改變行為，不能要求每場雜湊不變。
4. **修閃光資料模型與多顆威脅**：分清身份與時序，補 release 等號、不同反應值、兩顆相同／不同爆點、own+mate、延遲喊話測試，再評估是否維持提前放行。不要一次連煙的優先級一起改。
5. **修動態煙／敵情，再評估 B3**：加入過期煙、新燃火、無關路段火與封架點槍線的測試；將靜態候選快取與動態評分分開。先證明實際行為符合目的，再看強度。
6. **退役分支與低風險效能改動**：每批驗預設行為等價；先 dijkstra limit，再用空閒機器的正式沙箱側寫決定後續優先級。
7. **戰力驗收**：固定舊版及 2.5 為對手，v3/v5 交換兩側，預先固定訓練／保留種子；另跑兩張圖鏡像攻守窗口。以種子成對區間與預先定義的實用退化容許值報告，不以小樣本剛過 48% 作唯一結論。若仍要聲稱某項是退化根因，須同時有精確單變項對照與能連到丟失回合的時序證據。
