# 軍備競賽執行手冊

Oct 21, 2026 · @ALK

## 目的與準備

讓各家 AI 在相同條件下限時撰寫選手，產出「流派」：一條從 v1 到 vN 的版本成長線。M2 先試跑 2 家 AI × 2 種風格，驗證流程與規則文件。

### 參賽包（每次執行一份乾淨副本）

| 內容 | 說明 |
| --- | --- |
| spec.md | 規格書 v0.2（或當時最新版）中「選手需要知道」的部分 |
| bots/baseline.js | 基準 Bot 原始碼 |
| bots/template.js | 空白範例模板 |
| CLI | rts-sim 與使用說明 README |
| 回放播放器 | 本機可開啟的網頁 |
| versions/、CHANGELOG.md、BUGS.md | 空資料夾與空檔案，供 AI 填寫 |

### 公平條件

- 同一台機器、同一參賽包版本、同一時限。
- 每次執行之間不共享任何檔案。
- 除了下方規定的標準提示，不提供任何額外協助或提示。

## 風格方向清單

每次執行指定一種風格；風格必須能用 CLI 統計驗證，否則無法確認 AI 真的照做。

| 風格 | 說明 | 統計特徵 |
| --- | --- | --- |
| 速攻 | 早期集中兵力壓制，力求在對手成形前結束 | 首次造成傷害 tick 早（目標 < 1500） |
| 快速擴張 | 優先擴張與經濟，以後期兵力碾壓 | 首次擴張 tick 早、總採集量高 |
| 塔防龜縮 | 依隘口與防禦塔固守，等對手犯錯再反擊 | 防禦塔數量多、首次進攻晚 |
| 騷擾經濟 | 以騎兵等機動部隊攻擊對手工人與分礦 | 擊殺工人數高、騎兵比例高 |
| 適應反制 | 積極偵察，依對手兵種與節奏調整 | 偵察頻率高、兵種比例隨對手變化 |
| 控圖 | 佔領瞭望塔與富礦，以地圖控制取勝 | 瞭望塔佔領時間長、富礦採集比例高 |

M2 試跑建議用差異最大的「速攻」與「快速擴張」。

### 需要 CLI 補充的統計

開發任務書的 CLI 輸出尚缺以下欄位，M2 前需加入：防禦塔建造數、擊殺工人數、各兵種生產比例、偵察次數（戰鬥單位或工人進入敵方起點 15 格內的次數）、瞭望塔佔領 tick 數、富礦採集比例。

## 任務提示詞模板

每次執行只替換大括號內容；所有 AI 使用同一份模板，確保條件一致。

```markdown
你是 RTS 對戰選手 Bot 的開發者，正在參加一場 AI 選手競賽。

請先閱讀資料夾中的 spec.md（規格書）、bots/baseline.js（基準 Bot）、bots/template.js（範例模板）與 README（CLI 使用說明）。

任務：在 {時限} 內，撰寫一隻選手 Bot。
風格方向：{風格名稱}——{風格說明}

要求：
1. 符合 spec.md 的「選手模組限制」：單一檔案、不可 import、≤ 200 KB。
2. 1v1 對基準 Bot 勝率 ≥ 70%（以 rts-sim match --swap --games 50 驗證）。
3. 4 人局也要正常運作並爭取好名次。
4. 最終版本必須明顯體現指定風格。
5. 宣告 3～6 顆旋鈕，範圍內任何值都必須正常運作；旋鈕代碼與範圍在所有版本中保持一致。
6. 每次有明顯進步，就把當時的 Bot 存成 versions/vN.js，並在 CHANGELOG.md 記一行：版本、對基準 Bot 勝率、變更內容。每個快照都必須可正常執行。
7. 不得利用引擎漏洞；發現的漏洞或規格不清之處記在 BUGS.md。
8. 時限結束前交付 final.js 與 NOTES.md（策略概要、各旋鈕用途）。

請自行規劃時間，大量使用 CLI 自我對戰來迭代。
```

## 執行流程

1. 為每次執行準備一份乾淨的參賽包副本，命名為「AI 名稱\_風格\_日期」。
2. 記錄開始時間，貼上提示詞模板。
3. 執行中不提供任何協助；AI 提問規格問題時，只回答「以 spec.md 為準」，並把問題記錄下來作為規格修訂依據。
4. AI 在時限前停止時，送出標準續行提示：「時間還剩 {剩餘時間}，請繼續改進並保存新版本。」每次執行最多送 3 次。
5. 時限到即停止，保存整個資料夾。
6. 記錄：實際耗時、續行提示次數、提問內容、異常狀況。

## 評測流程

依序檢查，前一步不過就不必往下。所有對戰都用正式模式。

1. 合規：檔案大小、無 import、沙盒未偵測到禁用 API；final.js 與所有快照都能載入。
2. 最低標準：1v1 對基準 Bot 100 場（--swap），勝率 ≥ 70%。
3. 風格驗證：對照「風格方向清單」的統計特徵，與基準 Bot 及其他作品比較，確認差異明顯。
4. 版本線：每個快照對基準 Bot 跑 50 場，畫出勝率隨版本的變化；成長線應大致遞增，作為遊戲內升版路線。
5. 循環賽：所有最終版本進行 1v1 roundrobin 與 4 人局，產出勝率矩陣與 Elo。
6. 回放審查：觀看勝率最高、最懸殊、最膠著的幾場，檢查有無漏洞利用，並評估觀賞性。
7. 規則回饋：彙整 BUGS.md 與提問紀錄，決定規格書是否升版。

未達最低標準者可重跑一次；仍未達標則記錄原因，視為規則或文件的問題來源之一。

## 產出整理與規模規劃

每次執行整理成一份流派檔案，作為遊戲內容的原料。

### 流派檔案

| 欄位 | 內容 |
| --- | --- |
| 流派代號 | 內部識別碼 |
| 來源 | 撰寫的 AI、風格方向、規格書版本（僅內部記錄，遊戲內不顯示） |
| 風格描述 | 給玩家看的打法說明（人類選手口吻） |
| 版本列表 | 各快照的檔案、變更說明、對基準 Bot 勝率 |
| 旋鈕表 | 代碼、名稱、說明、範圍、預設值 |
| 評測摘要 | 統計特徵、循環賽成績、觀賞性評語 |

### 規模規劃

| 階段 | 規模 | 時限 | 目的 |
| --- | --- | --- | --- |
| M2 試跑 | 2 家 AI × 2 風格 ＝ 4 次 | 1～2 小時 | 驗證流程、規則文件、評測方法 |
| M5 正式 | 5 家 AI × 5～6 風格 ＝ 25～30 次 | 約 5 小時 | 產出遊戲內流派 |
| 改版（Patch） | 依需要 | 約 5 小時 | 規則改動後產生新流派、新 meta |

正式階段可在多台相同規格的機器上平行執行，以縮短總時程。
