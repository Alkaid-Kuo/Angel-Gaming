# 開發任務書 M0～M2

Oct 21, 2026 · @ALK

## 用途與工作方式

本文件給 Claude Code 實作 M0～M2：遊戲規則以「RTS 對戰引擎與選手 API 規格書 v0.2」為準，本文件補充實作層面的決定。兩者衝突時以規格書為準並回報。

### 工作方式

- 依里程碑順序進行，每個里程碑的過關條件達成才進入下一個。
- 遇到規格未定義或有多種合理做法的設計選擇，先列出 2～3 個方案比較，確認後再實作。
- 數值一律集中在單一設定檔，不散落在程式碼中。

### 程式風格

- TypeScript strict 模式；明確標註型別，不用 any，不用 var。
- Fail Fast：違反前提的狀況直接拋出例外。除非該值被刻意設計為可為空，否則不加 null 檢查。
- 核心邏輯（core）禁止：Math.random、Date、performance、浮點除法結果直接存入狀態。整數除法使用統一的輔助函式。
- 迭代順序必須確定：遍歷實體一律依 id 排序，不依賴 Map／Set 以外的物件鍵順序。

## 技術選型與模組架構

引擎以 TypeScript 撰寫，同一份 core 同時在 Node（CLI、正式比賽）與瀏覽器（遊戲、回放）執行。

### 技術選型

| 項目 | 選擇 | 理由 |
| --- | --- | --- |
| 語言 | TypeScript（strict） | 型別安全，Node 與瀏覽器共用 |
| 選手語言 | JavaScript（ES2020） | 參賽 AI 撰寫門檻低，日後 Unity 以 Jint 執行 |
| 執行環境 | Node 20+、現代瀏覽器 | — |

## tick 更新順序與核心演算法

每個 tick 依固定順序處理，所有同層處理依 id（或 playerId）由小到大，確保結果確定。

### tick 更新順序

1. 指令額度回補：tick 為偶數時，每位選手額度 +1（上限 5）。
2. 決策：tick 為 5 的倍數時，對每位存活選手依 playerId 順序建立觀察資料（反映上一 tick 結束時的狀態）、呼叫 decide、依序驗證並套用指令。正式模式可平行呼叫，但套用一律依 playerId 順序。
3. 生產進度推進；完成者生成單位。
4. 建造進度推進；完工處理。
5. 採集狀態機：開採計時、交付入帳、枯竭轉移。
6. 單位 AI：依姿態與目標規則選定目標與移動意圖。
7. 移動：沿路徑前進，之後做一次碰撞推擠。
8. 攻擊：冷卻歸零且目標在射程內者造成傷害（先累積）。
9. 結算傷害：移除死亡者、產生事件；檢查並處理淘汰。
10. 瞭望塔佔領進度。
11. 視野更新與敵方建築記憶。
12. 結束判定。

### 尋路

- 8 方向 A\*，整數成本：直線 10、斜向 14；樹林格成本 ×5÷3（直線 17、斜向 23）。
- 啟發函式為 octile 距離；同分時依 f、h、格索引順序決勝，確保確定。
- 禁止斜向穿過兩個阻擋格（或建築）之間的縫隙。
- 路徑快取於單位，目的地改變或路徑被新建築阻擋時重算。
- pathDistance 回傳幾何長度：直線段 1000、斜向段 1414（單位）。
- M3 單位數上升後再評估流場（flow field）。

### 空間索引

以 4×4 格為一桶的均勻格網索引單位位置，用於索敵、碰撞、視野查詢；每 tick 移動後更新。

### id 與亂數

- 單位、建築、礦點共用一個遞增整數 id 計數器，從 1 開始。
- 引擎亂數使用可序列化狀態的 PRNG（例如 xoshiro128 或 mulberry32），種子來自比賽 seed。
- 選手的 random() 使用獨立 PRNG，種子為 hash(matchSeed, playerId)。

## 地圖生成演算法

只為第 0 號扇區產生「物件清單」，再把每個物件旋轉複製到其他扇區；物件的聯集對旋轉不變，因此對稱自動成立。

### 旋轉公式（尺寸 N）

- 180°：(x, y) → (N−1−x, N−1−y)
- 90°：(x, y) → (N−1−y, x)，重複套用得到 4 個扇區
- 多格物件（建築、礦區）旋轉其所有佔用格，再取新的左上角。

### 步驟

1. 全圖初始化為平地；地圖外圍視為阻擋。
2. 起點：扇區 0 的主堡中心約在 (N×0.18, N×0.18)，各軸隨機偏移 ±2 格。
3. 主礦區：4 個礦點排成弧形，距主堡中心 6～7 格，位於背向地圖中心的一側，礦點間隔 1 格。
4. 基地平台：以主堡中心為圓心、半徑 11～13 格畫寬 2 格的阻擋環（被地圖邊緣截斷處不需補）；在朝向地圖中心 ±45° 的方向挖出寬 3～5 格的隘口。
5. 分礦區 2 處：位於環外、距主堡中心 16～22 格，分別偏向兩側；每處 4 個礦點，並保留 6×6 格空地供建築。4 人局時須留在自己的扇區內。
6. 富礦區：2 個富礦點，位於地圖邊緣中段附近、相鄰兩起點之間。
7. 瞭望塔：地圖正中心的點 (N×500, N×500)。
8. 障礙：在扇區內隨機放置斑塊（1v1 6 個、4 人 8 個），半徑 1～4 格；60% 為阻擋、40% 為樹林。另加 2～3 片較大樹林（半徑 2～5 格）。
9. 保護區不放障礙：基地環內、礦點周圍 2 格、分礦建築空地、瞭望塔半徑 4 格、隘口通道。
10. 將所有物件旋轉複製到其他扇區。
11. 驗證：洪水填充確認所有起點、礦點旁至少一格、瞭望塔互相連通；確認每個基地環有開口；確認對稱（每格與其旋轉對應格相同）。
12. 驗證失敗時以 hash(seed, 嘗試次數) 重新生成，最多 20 次；仍失敗則拋出例外。

### playerId 與起點

以引擎 PRNG 對起點槽位洗牌，依序分配給 playerId。

## 選手執行與沙盒

正式模式每位選手獨立 Worker 並計時；批次模式選手與引擎同一 Worker，以速度為優先。

### 模組格式

- 選手檔案為 ES module，default export 一個 class，提供 declare()、init(開局資料, 輔助工具)、decide(觀察資料) 三個方法。
- 每場比賽為每位選手建立一個新實例；實例的欄位即選手記憶。
- 基準 Bot 與範例模板即為格式示範，隨參賽包提供。

### 正式模式（Node）

- 每位選手一個 worker\_threads Worker。
- 決策 tick：主執行緒把觀察資料（structured clone）同時送給所有選手，等待回傳。
- Worker 內以 performance.now 量測 decide 耗時並回報；超過 5 ms 則該次指令作廢。
- 主執行緒設 50 ms 硬計時；逾時即 terminate 該 Worker，選手整場閒置，記錄 hardKilled。
- Worker 啟動時將 Math.random、Date、performance（量測用除外）替換為呼叫即拋例外的函式，違規立即暴露。

### 批次模式

- 引擎與所有選手在同一 Worker，直接函式呼叫；觀察資料仍為深拷貝，防止選手修改引擎狀態。
- 不做 5 ms 軟計時；50 ms 硬上限以每次呼叫後檢查耗時的方式處理（超過即該選手整場閒置）。
- 用於遊戲內練習賽研發、NPC 比賽、bench。

### 瀏覽器

- 遊戲與回放播放器使用批次模式，在 Web Worker 中執行引擎。
- 練習賽研發依 navigator.hardwareConcurrency 開多個 Worker 平行跑。

## CLI 規格

指令名稱暫定 rts-sim，提供對戰、循環賽、地圖檢視與效能量測四個子指令；輸出 JSON，供人與 AI 分析。

### 子指令

| 子指令 | 主要參數 | 用途 |
| --- | --- | --- |
| match | --mode 1v1／ffa4、--bots 檔案…（2 或 4 個）、--games N、--seed S、--swap、--exec official／batch、--knobs、--replay-dir、--out | 指定選手對戰 N 場 |
| roundrobin | --bots 檔案…、--mode、--games 每組場數、--seed、--exec、--out | 循環賽，輸出勝率矩陣與 Elo |
| mapgen | --mode、--seed、--format ascii／png、--validate N | 檢視地圖；或驗證 N 個 seed 的生成結果 |
| bench | --mode、--games、--exec batch | 基準 Bot 鏡像對戰，回報每秒場數與每秒 tick |

- 第 i 場的 seed ＝ S ＋ i；未給 S 時隨機產生並寫入輸出。
- --swap：1v1 時每個 seed 打兩場並交換起點。
- --knobs：為各選手指定旋鈕值（JSON），未指定用預設值。
- 結束碼：0 成功、1 參數錯誤、2 選手載入失敗、3 引擎內部錯誤。

### 每場輸出

| 欄位 | 內容 |
| --- | --- |
| seed、mode、engineVersion、specVersion | 比賽識別 |
| durationTicks、wallMs | 比賽長度與實際耗時 |
| players\[\] | 每位選手：bot 名稱與版本、playerId、起點、名次、淘汰 tick、資產分數 |
| players\[\].stats | 總採集量、生產單位數、損失單位數、擊殺數、建造建築數、首次擴張 tick、首次造成傷害 tick、APM、各代碼拒絕次數、軟超時次數、例外次數、是否被硬終止 |

### 彙總輸出

- 1v1：各選手勝率與場數。
- 4 人：平均名次與名次分布。
- roundrobin：勝率矩陣、Elo 排名。

## 回放格式與回放播放器

回放只保存 seed 與指令紀錄，播放時以引擎重新模擬；定期的狀態雜湊用來偵測不同步。

### 回放檔內容（JSON，可 gzip）

| 區塊 | 內容 |
| --- | --- |
| header | engineVersion、specVersion、mode、seed、players（playerId、bot 名稱、版本、初始旋鈕） |
| decisions | 每次決策：tick、playerId、原始指令陣列、旋鈕變更（若有）、是否作廢 |
| hashes | 每 100 tick 的狀態雜湊 |
| result | 名次、最終狀態雜湊 |

版本不符時拒絕播放並明確提示。

### 回放播放器（瀏覽器）

- 載入回放檔，在 Worker 中重新模擬並繪製。
- 控制：播放／暫停、0.5x～8x、跳轉（每 600 tick 存快照，跳轉時從最近快照重算）。
- 視角：上帝視角或任一選手視角（顯示該選手的迷霧）。
- 資訊：選手列（礦、人口、兵力值）、小地圖、事件記錄。
- 雜湊不符時停止並顯示不同步的 tick。

## 基準 Bot

基準 Bot 是「會正常運營但沒有戰術」的對手：不偵察、不擴張、不蓋塔，只做固定節奏的經濟與一波波進攻。

### 行為

1. 經濟：主堡持續生產工人至「工人上限」；新工人平均分配到主礦區礦點（每礦點最多 2 人）。
2. 人口：人口餘額 ≤ 4 且沒有補給站在建時，派一名工人在主堡附近蓋補給站。
3. 兵營：工人數達 8 且礦 ≥ 150 時蓋 1 座兵營；之後不再增加。
4. 生產：兵營依「弓兵比例」輪流生產長槍兵、弓兵、騎兵（預設 長槍 2：弓 2：騎 1）。
5. 進攻：戰鬥單位人口達「進攻門檻」時，全軍攻擊移動到最近的敵方起點；之後新單位的集結點設為該處。
6. 防守：主基地範圍內的建築或工人受攻擊時，所有未出征的戰鬥單位攻擊移動到受攻擊處。
7. 4 人局：進攻目標為路徑距離最近且仍存活的敵方起點。

### 旋鈕

| 代碼 | 名稱 | 範圍 | 預設 |
| --- | --- | --- | --- |
| attackThreshold | 進攻門檻（戰鬥單位人口） | 6～30，整數 | 12 |
| workerCap | 工人上限 | 8～24，整數 | 16 |
| archerRatio | 弓兵比例（%） | 0～80，整數 | 40 |

### 定位

- 目標：寫得好的選手能穩定擊敗它（≥ 70%），但不能被完全無腦的打法擊敗。
- M2 前以「隨機 Bot」與幾個簡單腳本驗證：基準 Bot 對隨機 Bot 應接近 100% 勝率。

## M1 人類操作介面

人類玩家透過與選手相同的指令介面操作，因此人類對局也能錄成回放；M1 的目標是讓開發者親手驗證好不好玩。

### 畫面

- Canvas 2D 俯視圖，1 格 ＝ 16 px（縮放 1x），支援縮放與平移（WASD、畫面邊緣、中鍵拖曳）。
- 地形：平地、阻擋、樹林以不同底色；礦點、瞭望塔以圖示。
- 單位：隊伍色圓形＋兵種記號（工人小點、長槍兵直線、弓兵圓環、騎兵大圓）；血條；選取框。
- 建築：隊伍色矩形＋代碼字母；建造中以半透明與進度條表示。
- 迷霧：未探索全黑、不可見半暗。
- HUD：礦、人口、遊戲時間、事件記錄、小地圖、選取資訊與可用動作。

### 操作

| 操作 | 效果 |
| --- | --- |
| 左鍵拖曳／點擊 | 選取 |
| 右鍵（空地） | 移動 |
| 右鍵（礦點，選工人） | 採集 |
| 右鍵（敵方） | 攻擊 |
| 右鍵（己方未完工建築，選工人） | 接續建造 |
| A ＋ 左鍵 | 攻擊移動 |
| H | 駐守 |
| F1～F4 | 姿態：積極、防守、堅守、撤退 |
| Ctrl ＋ 0～9／0～9 | 設定編隊／選取編隊 |
| B ＋ 建築鍵 ＋ 左鍵 | 選工人後放置建築（顯示可否放置） |
| Q／W／E | 選建築時生產對應單位 |
| 右鍵（選建築時） | 設定集結點 |
| 空白鍵 | 暫停；＋／− 調整速度 0.5x～4x |

### 對局設定

- 人類 vs 基準 Bot（1v1）、人類 vs 3 個基準 Bot（4 人）。
- 人類的指令額度預設不限制，可在設定中開啟與選手相同的限制。

## 測試計畫與效能基準

確定性是整個專案的地基：回放、練習賽研發、正式排名都依賴它，因此確定性測試必須在 M0 完成並持續執行。

### 確定性

- 同 seed ＋ 同指令序列連跑 3 次，每 100 tick 狀態雜湊完全一致。
- Node 與瀏覽器執行同一回放，雜湊一致。
- 正式模式錄製的回放，以回放重建後最終雜湊一致。

### 規則單元測試

- 傷害計算：所有攻擊方 × 目標組合符合倍率表。
- 採集：單一工人在已知距離下，每分鐘產量符合計算值；礦點排隊、枯竭轉移。
- 生產與建造：時間、扣款時機、取消退款、人口計算。
- 指令額度：令牌桶回補與 NO\_BUDGET。
- 單位 AI：各姿態的追擊範圍、目標選擇五層順序。
- 瞭望塔佔領與重置；勝負判定與名次計算（含同 tick 淘汰）。

### 地圖生成

- 每種規模 1000 個 seed 全部通過驗證，且重試次數分布有記錄。
- 對稱檢查：每格與其旋轉對應格相同。

### 沙盒

- decide 超過 5 ms：指令作廢。
- 無窮迴圈：50 ms 被終止，比賽正常結束。
- 拋例外：比賽繼續。
- 使用 Math.random、Date：立即拋例外並記錄。

### 效能基準（M0 目標）

| 情境 | 模式 | 目標 |
| --- | --- | --- |
| 基準 Bot 鏡像 1v1 | 批次、Node 單核 | ≥ 5 場／秒 |
| 基準 Bot 鏡像 4 人 | 批次、Node 單核 | ≥ 1 場／秒 |

未達標時優先檢查：路徑快取命中率、空間索引、觀察資料深拷貝成本。實測值決定遊戲內「每週練習賽場數」的換算。
