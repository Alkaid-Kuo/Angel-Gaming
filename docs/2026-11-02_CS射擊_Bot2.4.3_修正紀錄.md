## 修正範圍

- `defuseTeam()` 為集結、拆包分工與進點順序共用的逐人完成時間模型。只採存活者，各自使用自己的／公開已知隊友 kit；死亡者與來不及者不參與等待。已開始拆包、已有待執行拆包或時間緊迫時立即 go。正常有餘裕的多人集結仍保留。
- 清理死亡者的 kit 記憶，忽略死亡者延遲抵達的 kit 喊話；即使還未清理記憶，完成時間模型也不採計死人，並非只改成「有任何活人有 kit」。
- go 後等待突破手的條件也使用同一可行候選，避免集結已放行，卻又等來不及的突破手。

## 更正延遲說明與臨界策略

2.4.2 報告將 `rules.reactionTicks` 稱為公開上界，**不正確**。它是 `reactionTicksFor()` 的四捨五入值；屬性驅動的實際延遲依 `reactionEighths()` 每批機率式進位。例如 reaction=69，公開值 5，實際可為 5 或 6。舊版逐 tick 專項只有固定五 tick，不能當成屬性驅動延遲的驗證。同步更正 `RulesInfo.reactionTicks` 的 API 註解；欄位、版本與執行行為不變。

2.4.3 只使用公開 init 屬性、已記載公式與公開值推算可能區間。若公開值與屬性公式不一致，按明確整數覆寫處理；若一致，區間同時容納屬性進位與同值整數覆寫的可能，無法從 API 預知本批進位結果。隊友屬性不公開，其延遲沿用本人區間作估計，不能稱為保證。

- 集結看較慢端估計與既有裕度，避免把不確定性當成可繼續等待的餘裕。
- 拆包候選保留最早端仍可能完成的人，優先較慢端也來得及者；僅剩機率性機會時立即嘗試。
- 時間可行性的臨界判準採**盡力嘗試**，不宣稱必定拆成；既有戰力不利時保槍與致命自保判斷仍保留。進行中的本人拆包則依實際公開進度精算，不能因尚未抽出的延遲取消。
- 不讀取驅動層私有佇列或 PRNG 狀態；不改引擎、API、地圖、角色屬性與既定平衡門檻。
