## 一、目標

把赤岩舊城做成**正式可用的第二張地圖**，並把「編輯器改圖 → 檢查 → Bot 大樣本 → 登錄 → 試玩選圖」這條流程做成之後每張新圖都走的路。預設地圖**不換**，換預設是使用者在看過大樣本與實玩後另外決定的事。

### 使用者定下的地圖設計原則（最高優先）

1. **不做死巷房間**：每個空間都要連通成路線，沒有單門的死路房。
2. **掩體只放交戰點**：不是到處擺箱子。
3. **不用 Bot 使用率判斷房間價值**：Bot 不走某個房間不代表房間沒用，房間價值由路線結構決定。
4. 骨架維持方案第一節：北 CT、南 T、A 東、B 西，三條主路、兩條橫向連接，每個包點三個入口。

### 驗收表

| 項目 | 門檻 |
| --- | --- |
| JSON 地圖進引擎 | 編輯器存的 JSON（`MapLayout` 格式）能被引擎載入：`maps/shooter/*.json` 是編輯器地圖的唯一來源，`MAPS` 多一個 `redrock2`（建置時匯入 JSON，或等價做法，報告說明）；`REDROCK_LAYOUT`、`DUST_LAYOUT` 與 `DEFAULT_MAP_ID` 不動 |
| 請求單帶地圖 | `MatchRequest` 加選用 `mapId`，缺值當 `redrock`；閘道照它建地圖；舊存檔、舊回放結果與雜湊不變（既有測試證明）；經營核心 `src/manage/` 仍無賽制專有字樣 |
| 試玩選圖 | 可玩版設定卡多「地圖」下拉（只加這幾行，介面語彙與版面不要動，另一個工作階段正在改整個試玩頁的美術）；`#watch` 由請求單決定地圖；CLI 的 `shooter` 子命令能指定地圖 |
| 編輯器檢查 | 最終地圖在編輯器 `analyze` 全部通過（死路 0、連通、出生點不互見、包點入口數、碎格、超長線、斜切格合法）；報告貼檢查表 |
| Bot 大樣本 | 基準 Bot 2.1 均衡 v3 對 v3，每張圖 ≥ 100 場（座位交換），報：例外／超時、T 回合勝率、下包率、A／B 分布、首次接觸秒數、換血率、回防成功率、加時場數；與赤岩鎮同條件對照；陪練 Bot（`shooter-practice.js`）也跑 ≥ 30 場確認不卡不例外 |

## 二、步驟

1. 複製三個地圖 JSON 進分支並 commit；用編輯器開 `redrock2-v3.json` 跑檢查，截全圖；報告第一節先寫「現況」。
2. JSON 載入 → `MAPS.redrock2`；請求單 `mapId`；測試。
3. 試玩選圖與 `#watch`；CLI 地圖參數；在瀏覽器實際走一圈（兩隊各一次），確認出生、三條路、包點、下包拆包都正常。
4. Bot 大樣本（腳本加地圖參數，不改預設），整理數字。
5. 依數字與設計原則提出改圖建議（每條附理由、位置、預期影響、截圖）；**顯而易見的錯**（死路、碎格、檢查器報錯）可以直接改並逐條列出，**結構性的改動**（開新門、移掩體、改房間）寫成建議等使用者在編輯器裡決定。
6. 區域合併與 callout 清單；`material` 欄位與編輯器支援。
7. 文件、報告。

## 四、交付

- 分層 commit：地圖檔 → 任務書 → JSON 載入與登錄 → 請求單地圖欄位 → 試玩選圖與 CLI → 腳本地圖參數與大樣本 → 改圖（每次改圖一筆，說明改了哪裡為什麼）→ 區域與材質 → 文件 → 報告。
- 報告 `docs/2026-11-01_CS射擊_新地圖製作_交付報告.md`：驗收表逐項數據；大樣本對照表；編輯器檢查表；全圖截圖（改前改後）；改圖紀錄；**給使用者決定的事**（地圖正式名稱、是否換預設、結構性改圖建議清單）；**與任務書的出入逐條**；沒做到的項目。
- 最後訊息三句：commit 範圍、驗收是否全過、沒做到的項目。

## 五、規則

- `bots/` 凍結：Bot 在新圖出例外只回報、不改 Bot；`src/shooter/sim.ts`、`config.ts`、`api.ts` 不動；`map.ts` 只加 JSON 載入與選用欄位，不改既有地圖與斜切格行為。
- 確定性：地圖載入與建構不得引入 `Math.random`／`Date`；同一 JSON 永遠建出同一張圖（測試：兩次 `buildMap` 的 `solid` 相同）。
- 視野公平：地圖資料不得讓任何一方出生就看到對方；超長直線要有理由（長對線是規格允許的）。
- 經營核心不得出現賽制專有字樣。
- 不 push、不碰 main、不動軍團戰檔案；刪檔前先在回報裡說明並等使用者同意；**絕不修改 `cs-art-sketch-661c2e` 工作樹裡的任何檔案**。
