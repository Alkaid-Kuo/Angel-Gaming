# M0 實作決策紀錄

Oct 22, 2026 · 對應規格書 v0.2、開發任務書 M0～M2

本文件記錄 M0 實作時，規格書未定義、或規格書與任務書衝突之處的決定。規格書升版（v0.3）時，請把「規格補充」與「規格修正」兩節併入規格書。

## 一、開工前確認的決策（Q1～Q8，皆採建議方案）

| 代號 | 問題 | 決定 |
| --- | --- | --- |
| Q1 | 規格錯誤：射程判定為「攻擊方中心到目標邊緣」，但推擠會讓兩單位剛好相切，近戰（射程 200 < 半徑 300～450）永遠打不到 | 改為「雙方邊緣之間的距離 ≤ 射程」，數值不動；防禦塔仍從塔中心起算 |
| Q2 | init 的 1000 ms 軟上限與「任一進入點 50 ms 硬上限」衝突 | init 只有一道 1000 ms 上限（超過即終止並整場閒置）；50 ms 只管 declare 與 decide |
| Q3 | 任務書矛盾：批次模式同執行緒，無窮迴圈不會返回，「呼叫後檢查耗時」無法生效 | 批次模式照任務書做，文件註明擋不住無窮迴圈；CLI `match` 預設 `--exec official`，`bench` 與遊戲內用 batch |
| Q4 | 任務書矛盾：基準 Bot 工人上限 16，但主礦 4 點 × 每點最多 2 人 = 8 | 每礦點先放滿 2 人，之後平均加到 3、4 人 |
| Q5 | 規格缺漏：工人抵達後開工失敗要「發出事件」，但事件表沒有對應項 | 新增事件 `buildFailed`（工人 id、建築代碼、座標、原因 NO_MINERALS／BAD_PLACEMENT） |
| Q6 | 瞭望塔何時易主 | 照字面：他人一開始累積，原佔領者立即失去塔與視野；其他人的部分進度也一律歸零 |
| Q7 | 單位沿路徑移動的方式 | A\* 後拉直轉角；追擊時若視線無阻擋直接朝目標走、不重跑 A\*（重算間隔 5 tick） |
| Q8 | 工人收到攻擊移動時是否交戰 | 只有指定目標的 `attack` 會讓工人戰鬥；工人的 `attackMove` 等同 `move` |

## 二、規格補充（規格書未定義，M0 採用的做法）

### 選手 API

- **開局資料新增 `knobs`**：規格只在觀察資料提供旋鈕，開局規劃也需要。
- **宣告的 `version` 為選填**：規格的 declare 只列名稱、風格、旋鈕；版本號用於回放與統計輸出。
- **指令與觀察資料的欄位格式**：以 `src/api/types.ts` 為準（例如 `{ type: 'build', workerId, building, tileX, tileY }`）。M2 參賽包需把此檔整理進 spec.md。
- **`pathDistance` 參數為格座標**；起點或終點位於已知建築內時，該建築暫時視為可通行（否則從自己主堡出發永遠回傳 -1）；起訖點為地形阻擋或超出地圖回傳 -1。
- **`canPlace` 與引擎下指令時的放置驗證使用同一套規則**：地形為平地、無礦點、已探索、與「己方建築＋目前可見的敵方建築＋記憶中的敵方建築」不重疊。開工時再以真實狀態驗證。
- **選手模組嚴格採 ES2020**：類別欄位（`x = 1;`，ES2022）等較新語法會在載入時被拒；具名 export 允許但會被忽略。

### 規則細節

- **礦點排隊**：礦點空出時，由排隊順序中第一位「已在礦點旁」的工人開採。排在前面但被推擠離開的工人不會卡住後面的人。
- **枯竭的礦點仍是障礙物**（不可通行、不可建造）。
- **開局工人**：4 名出現在主堡外圈最接近主礦區的格，開局為閒置，須由選手下達 `gather`。
- **新單位出生**：建築外圈可通行格中最接近集結點（無集結點時朝地圖中心）者；四周被封住時暫停生產，等有空位。
- **建築被摧毀時的生產佇列**：不退礦，佔用的人口釋放。
- **「正在攻擊自己的敵人」判定**：該敵人在其冷卻時間內實際攻擊過自己。
- **擊殺歸屬**：致死 tick 對其傷害最高的選手；同分取 playerId 小者。
- **指令額度**：被拒的指令也扣 1 點（NO_BUDGET 除外）；軟超時作廢的指令不扣、不發事件。
- **地形碰撞只看單位中心點**；單位半徑只用於單位間推擠與射程。
- **視野**以觀察者所在格的中心為圓心；偶數尺寸建築與瞭望塔以格角為圓心，維持旋轉對稱。
- **移動取整**：方向分量向零取整，避免左右、上下移動量差 1 而破壞旋轉對稱的公平性。
- **地圖生成全程整數運算**（角度查表），確保不同 JS 引擎產生同一張地圖。

### 統計定義

| 統計 | 定義 |
| --- | --- |
| 首次擴張 tick | 在非己方主礦區的礦點 8 格內開工主堡或採集站的 tick |
| 首次造成傷害 tick | 第一次對敵方造成傷害的 tick |
| APM | 消耗額度的指令數（含被拒）÷ 比賽分鐘數 |
| 偵察次數 | 單位每次由外進入存活敵方起點（主堡中心）15 格內記一次 |
| 瞭望塔佔領 tick 數 | 身為佔領者的 tick 數 |
| 富礦採集比例 | 交付的富礦量 ÷ 總採集量 |
| 防禦塔建造數 | 完工的防禦塔數 |

## 三、實作層面的決定

- **TypeScript 原始碼直接以 Node 22.18+ 執行**（型別剝除），`npm run build` 另產生 `dist/` 供 Node 20 使用。
- **路徑快取**：全域以（起點格, 目標矩形）為鍵；任何建築新增或移除都會清空，因此快取對結果透明（不影響確定性）。
- **空間索引**：4×4 格一桶，以計數排序重建，桶內依 id 排序。
- **回放**：空的決策不記錄；作廢的決策記錄但不套用；hash 涵蓋所有影響後續模擬的狀態。
- **選手隔離**：批次模式以函式參數遮蔽 `Math.random`、`Date`、`performance`、`process` 等全域；正式模式另在 Worker 內替換真正的全域。兩者都是防呆，不是安全邊界。

## 四、M1～M3 的決定（夜間自主進行，待你審閱）

### M1 人類可玩

- **人類指令的時機**：與選手相同，介面送出的指令在下一個決策 tick（每 0.5 秒）套用，因此人類對局也能完整錄成回放；代價是操作最多延遲 0.5 秒。
- **鏡頭鍵衝突**：WASD 平移與 A（攻擊移動）、W（生產弓兵）衝突；有對應動作時優先執行動作，方向鍵永遠是平移。
- **建築鍵**：B 之後 C 主堡、D 採集站、S 補給站、R 兵營、T 防禦塔（M3 加 F 鍛造所、G 攻城工坊）；X 取消；U 升級主堡。
- **回放跳轉**：每 600 tick 存一份狀態深拷貝，跳轉時從最近快照重算。
- **跨環境確定性**：瀏覽器（Chromium 核心）重建 3 個 Node 產生的回放，每 100 tick 雜湊與最終雜湊全部一致；Firefox／Safari 尚未驗證。

### M2 小規模軍備競賽

- **`--swap` 的 `--games`**：代表總場數（須為偶數），每個 seed 打兩場並交換起點。手冊的「--swap --games 50」即 25 個 seed × 2。
- **`roundrobin`**：1v1 每組選手同 seed 交換起點各一場；4 人局為所有 4 人組合。Elo 以 Bradley–Terry 最大概似估計（與比賽順序無關），換算為平均 1500 的尺度。
- **參賽包**：`npm run pack:build` 產生，可在任何資料夾以 Node 20＋執行；回放播放器以 `rts-sim viewer` 開本機伺服器（瀏覽器的 Worker 不能從 file:// 載入）。
- **試跑的「兩家 AI」**：Claude（Opus 子代理）與本機 Qwen3.8-27B（opencode CLI，llama.cpp 64k 上下文，約每秒 12 token）。
- **平衡觀察**：攻擊門檻 30、工人上限 8 的基準 Bot 對預設基準 Bot 4 戰全勝——囤兵後出擊明顯優於 12 人口就出擊。

### M3 觀戰體驗與延後內容

- **自動導播**：跟著交戰熱點（10 格區域內的攻擊次數）走；每個鏡頭至少停 4 秒，除非新熱點強度達 2 倍；沒有交戰時看兵力最多的部隊。使用者手動移動鏡頭即切到自由鏡頭。
- **精華模式**：沒有交戰時自動以 8 倍速快轉。**跳到下一次交戰**：快轉到交戰強度超過門檻。**直接看結果**：快轉到結束。
- **8 人局**：方格地圖無法做 45° 旋轉，改用 90° 旋轉＋對角鏡射；相鄰起點只隔約 40 格，分礦改朝地圖中心兩側。
- **主堡升級、鍛造所、攻城車**：數值見規格書 v0.4（全部標示提案）。攻城車初版太強（3 台 5 秒拆塔），已調弱為血量 200、冷卻 30、防禦塔對攻城車 200%。
- **研究強度**：護甲 +1 就讓 10 對 10 同兵種從勢均力敵變成存活 4～6 比 0，偏強；先維持提案，等實戰資料再調。
- **id 順序偏差**：鏡像的 10 對 10 近戰，id 較大的一方會剩 2～3 隻（推擠依 id 順序處理）。正式比賽單位 id 會交錯，影響應較小；之後可評估改為同時結算推擠。
- **收縮機制**：企劃書列為待決定，未實作。
- **戰術暫停**：屬於經營層（M4），M3 未做。
