## 七、已知問題、風險與待決事項

**安全與公平（誠實版）**
1. **黑盒靠自律＋事後稽核**。選手與裁判在同一個 Windows 帳號下，整個硬碟都讀得到。隔離只做了兩件事：bot 在受限子程序執行（`--permission`、無子程序、無 worker、環境變數幾乎為空）、對手池加密。**沒有做 OS 層隔離（D03）**：bot 仍可連 `127.0.0.1` 的網路；明文來源仍在 `archive\round-00`、`round-01`、`archive\legacy\Legion-Claude_舊`（2026-10-25 從 Sandbox 頂層搬進來）等處；選手可以讀硬碟上任何檔案，只靠規則禁止與稽核。
2. **對話紀錄互相可讀**。`~\.claude\projects\` 與 `~\.codex\sessions\` 彼此可讀。所以**不要在對話裡輸出代號、標籤、金鑰、憑證、保密種子**。
3. Claude Code 的「略過權限確認」模式：使用者在 設定 → Claude Code 開啟後，我曾把 Claude 選手切成 bypass，但使用者回報仍會跳批准（原因：已啟動的工作階段沒有套用變更）。**現在不需要 bypass**：第 4 項的 allow 規則已解決。禁止規則在 bypass 下是否仍有效仍未驗證，所以**不要用 bypass**，維持預設模式加 allow／deny 規則。

**營運**
4. **權限批准造成的停頓（已於 2026-10-25 修正並驗證）**：第 1 輪 Claude 選手的專案設定只有 deny 規則、沒有 allow 規則，預設每個指令都要批准，使用者睡著時卡了約 7.4 小時，補時處理。**根因**：已啟動的工作階段不會套用事後新增的設定（`settings.local.json`、切換模式都無效或不穩）。**修正**：在選手包的設定範本 `arena\templates\claude-settings.json` 加入 `allow: ["Bash","Edit","Write","NotebookEdit","Read","Glob","Grep"]`（deny 規則仍優先），重建 `pack-claude`、重新部署 `Legion-Claude\.claude\settings.json` 與 `MANIFEST.sha256`（可信基線已隨 `build-pack` 更新）。**驗證**：新開的 Claude Code 工作階段（預設模式、haiku、cwd=`Legion-Claude`）自動完成 `node -v`、用 heredoc 寫入 `/tmp`、讀回，全程沒有要求批准；讀取 `Legion-Arena\README.md` 與 `ls Legion-GPT` 都被 deny 規則擋下。**注意**：選手工作階段必須在設定部署**之後**才新開；若使用者沿用舊工作階段，仍會跳批准。另外，本批已同步正式 allow 清單並更新搬移後禁止路徑、修正共同父目錄的 Bash 誤擋；部署後仍須使用全新 Claude 工作階段實測，不能據此宣稱 OS 隔離。稽核選手紀錄時，`C:\Users\User\.claude\projects\C--Claude-Sandbox-Legion-Claude\` 內 2026-10-25 約 16:00 的「權限修正驗證（探測）」紀錄是裁判的測試，忽略即可。
