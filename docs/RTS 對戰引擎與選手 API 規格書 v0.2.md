# RTS 對戰引擎與選手 API 規格書 v0.2

Oct 21, 2026 · @ALK

## 文件說明

本文件同時是引擎的實作規格，也是給各家 AI 撰寫選手 Bot 的規則文件；範圍為 MVP（里程碑 M0～M2）。實作細節（模組、更新順序、地圖生成演算法）另見「開發任務書」。

- MVP 範圍：1v1 與 4 人混戰；工人＋三種戰鬥兵種；五種建築；無科技升級。
- 所有數值為初始值，平衡測試後調整；調整時版號遞增。

### v0.2 相對 v0.1 的變更

| 項目 | 變更 |
| --- | --- |
| 瞭望塔 | 改為地圖中心的一個「點」（單位座標），不佔格、不阻擋；以佔領半徑判定 |
| 時間上限 | 新增硬上限 50 ms：超過即終止該選手，整場剩餘時間閒置 |
| 執行模式 | 區分正式模式（隔離、計時）與批次模式（無計時），正式比賽一律在 Node 執行 |
| 選手模組 | 單一檔案、不可 import、≤ 200 KB |
| 起點分配 | 每場依 seed 隨機分配 playerId 與起點 |

## 基本單位

全部狀態以整數表示：時間用 tick，長度用「單位」，確保不同平台結果一致。

| 項目 | 定義 |
| --- | --- |
| tick | 邏輯更新一次；1 秒 ＝ 10 tick |
| 格 | 地形格子；1 格 ＝ 1000 單位 |
| 座標 | 原點在地圖左上角，x 向右、y 向下；單位位置為整數單位座標 |
| 格座標 | tileX ＝ floor(x ÷ 1000)，tileY ＝ floor(y ÷ 1000) |
| 距離 | 歐氏距離；比較時用平方值，需要實際長度時用整數平方根（向下取整） |
| 百分比 | 倍率以整數百分比表示（×1.5 ＝ 150），計算後向下取整 |

本文件中的「秒」「格」皆為方便閱讀，實作一律換算為 tick 與單位。

## 地圖

每場程序生成、依人數旋轉對稱；地形、礦點、瞭望塔與所有起點在開局時全部公開。

### 尺寸

| 規模 | 尺寸（格） | 對稱方式 |
| --- | --- | --- |
| 1v1 | 64 × 64 | 繞中心旋轉 180° |
| 4 人 | 96 × 96 | 繞中心旋轉 90° |

### 地形

| 地形 | 代碼 | 通行 | 可建造 | 視野 |
| --- | --- | --- | --- | --- |
| 平地 | 0 | 可 | 可 | 正常 |
| 阻擋（懸崖、水） | 1 | 不可 | 不可 | 不阻擋 |
| 樹林 | 2 | 可，速度 ×60% | 不可 | 見「戰鬥、視野」 |

### 地圖物件

| 物件 | 數量 | 說明 |
| --- | --- | --- |
| 起點 | 每人 1 | 主堡預設位置，位於隘口後方 |
| 主礦區 | 每人 1 | 起點旁，4 個礦點 |
| 分礦區 | 每人 2 | 隘口外，各 4 個礦點 |
| 富礦區 | 每人份 1 | 中立位置，2 個富礦點 |
| 瞭望塔 | 1 | 地圖正中心的一個點，佔領半徑 3 格，不佔格、不阻擋 |

- 礦點佔 1 格，不可通行、不可建造。
- 一般礦點儲量 1000；富礦點儲量 1200。
- 礦區以 areaId 分組。
- playerId 與起點的對應每場依 seed 隨機分配。

### 生成保證

- 所有起點、礦區、瞭望塔彼此連通。
- 因旋轉對稱，各起點到各自主礦、分礦與瞭望塔的路徑距離相同。
- 每個起點有至少一個寬 3～5 格的隘口。
- 同一 seed 產生同一張地圖。

## 經濟

唯一資源為「礦」；工人往返礦點與卸貨點的循環由引擎自動執行，選手只決定派誰去哪個礦點。

### 採集循環

1. 工人走到指定礦點旁（距離礦點邊緣 ≤ 200 單位）。
2. 開採 20 tick，取得 5 礦（富礦點 8 礦）；礦點儲量同步扣除。
3. 走回最近的己方已完工卸貨點（主堡或採集站），交付後資源入帳。
4. 自動回到同一礦點，重複循環。

- 每個礦點同時只能有 1 名工人開採，其他工人排隊等候；每礦點約 2 名工人即接近飽和。
- 礦點枯竭時，該礦點的工人自動改採同礦區最近的未枯竭礦點；整區枯竭則閒置並發出事件。
- 工人在採集途中被下達其他指令即中斷循環；已攜帶的礦保留，下次到卸貨點時交付。

### 人口

| 來源 | 人口上限 |
| --- | --- |
| 主堡（每座） | +10 |
| 補給站（每座） | +8 |
| 全場硬上限 | 每位選手 50 |

建造中的建築不提供人口；人口不足時無法排入生產。

### 開局

主堡 1 座（位於起點，已完工）、工人 4 名（主堡旁）、礦 100。

### 建造規則

- 由 1 名工人建造；工人須移動到建築邊緣 ≤ 200 單位處，建造期間該工人不可做其他事。
- 資源不在下達指令時扣除，而在工人抵達並開工時扣除；屆時不足則指令失敗並發出事件。
- 建造時血量從 10% 線性增加到 100%；可被攻擊、可被摧毀。
- 建造中途工人被改派，建造暫停；任何己方工人可接續。
- 取消建造退還 75% 成本（向下取整）。
- 放置條件：所有佔用格皆為平地、無其他建築與礦點、在己方已探索區域內；單位位於該處會被推開。

### 生產規則

- 每座建築的生產佇列上限 5；排入時立即扣除成本與人口。
- 取消佇列項目（含正在生產者）全額退還。
- 完成的單位出現在建築邊緣最接近集結點的空位；若有集結點則自動移動過去。

## 戰鬥、視野、移動與碰撞

戰鬥完全確定：無命中率、無暴擊、無投射物飛行時間，勝負只取決於決策。

### 傷害

- 傷害 ＝ floor(攻擊 × 倍率 ÷ 100)，最低 1。MVP 無護甲。
- 攻擊瞬間生效（含遠程）；冷卻結束才能再次攻擊。
- 射程判定：攻擊方中心到目標邊緣的距離（單位為圓，建築為矩形）≤ 射程。
- 攻擊需要目標位於己方視野內。
- 同一 tick 的傷害全部結算後才移除死亡者，同歸於盡是可能的。

### 視野與迷霧

- 單位與建築以自身中心為圓心，視野半徑內的格子可見；建造中建築視野減半。
- 樹林格：只有觀察者距離該格 ≤ 2 格時才可見；觀察者自己在樹林中，看外面不受影響。
- 懸崖與水不阻擋視野。
- 迷霧三態：未探索 → 已探索但不可見（保留最後看到的敵方建築）→ 目前可見。
- 佔領瞭望塔者獲得以塔為中心、半徑 12 格的視野。

### 瞭望塔佔領

- 佔領半徑 3 格內只有某一選手的單位（工人不算）時，該選手佔領進度每 tick +1；達 100 即佔領。
- 範圍內有多名選手的單位、或無人時，進度不變；他人開始累積時，原佔領者的進度歸零。
- 瞭望塔不可被攻擊或摧毀。

### 移動

- 尋路：在格子上做 8 方向 A\*，不可穿過阻擋格與建築的對角縫隙；尋路不考慮其他單位。
- 每 tick 沿路徑移動「速度」單位；在樹林格內速度為 floor(速度 × 60 ÷ 100)。
- 目的地不可到達時，移動到最接近的可到達點。

### 碰撞

- 單位以圓形碰撞；允許重疊，每 tick 移動後做一次推擠：重疊的兩單位各被推開重疊量的一半。
- 推擠依單位 id 由小到大依序處理，確保結果確定。
- 正在開採或建造的工人不被推動。
- 單位不可進入阻擋格與建築；被推入時退回原位置。

## 通用單位 AI 與勝負判定

選手只下高階指令與姿態，個別單位的索敵、追擊、反擊由引擎以同一套規則處理。

### 姿態

| 姿態 | 代碼 | 行為 |
| --- | --- | --- |
| 積極（預設） | aggressive | 自動攻擊視野內敵人；從開始追擊處起最多追 8 格，超過則放棄並返回 |
| 防守 | defensive | 只攻擊射程內敵人；離駐守點不超過 3 格，打完回到駐守點 |
| 堅守 | hold | 原地不動，只攻擊射程內敵人 |
| 撤退 | retreat | 移動途中完全不攻擊、不停留 |

駐守點：下達移動、攻擊移動或駐守指令後，單位停下的位置。

### 指令與自動行為

- 移動：沿途不主動攻擊；抵達後依姿態行動。
- 攻擊移動：沿途依姿態自動交戰，敵人消失後繼續前往目的地。
- 攻擊指定目標：持續追擊直到目標死亡或離開視野，不受追擊距離限制。
- 閒置：依姿態自動交戰。

### 目標選擇

依序比較，前一項相同才看下一項：

1. 正在攻擊自己的敵人優先。
2. 類別：戰鬥單位 > 工人 > 建築。
3. 有兵種倍率優勢（倍率 > 100）者優先。
4. 距離較近者優先。
5. id 較小者優先。

已有目標時，除非目標死亡、離開視野或超出追擊範圍，否則不換目標。

### 工人與防禦塔

- 工人自動執行採集循環；被攻擊時不逃跑也不反擊，只在被下達攻擊指令時戰鬥。
- 防禦塔自動攻擊射程內敵人，目標選擇同上。

### 勝負判定

- 時限：6000 tick（10 分鐘）。
- 淘汰：主堡（含建造中）全數被摧毀即淘汰，其餘單位與建築一併移除。
- 淘汰者名次依淘汰時間，越晚越前；同 tick 淘汰者依資產分數比較。
- 時限到時存活者依資產分數排名：存活單位成本總和 ＋ 已完工建築成本總和；未花用的礦不計。
- 仍同分時，依比賽 seed 確定性抽籤。
- 1v1 一方淘汰即結束；4 人局剩 1 人即結束。

## 選手 API：生命週期與資料

選手是一個 JS 模組，提供宣告、開局分析、決策三個進入點；選手物件在整場比賽中存活，可自由保存記憶。

### 生命週期

| 進入點 | 呼叫時機 | 輸入 | 輸出 | 軟上限 |
| --- | --- | --- | --- | --- |
| declare | 載入時 | 無 | 流派名稱、風格描述、旋鈕表 | — |
| init | 開局 tick 0 前，一次 | 開局資料、輔助工具 | 無 | 1000 ms |
| decide | 每 5 tick（tick 0、5、10…） | 觀察資料 | 指令陣列 | 5 ms |

### 開局資料

| 欄位 | 內容 |
| --- | --- |
| width、height | 地圖尺寸（格） |
| tiles | 地形陣列，長度 width × height，索引 ＝ tileY × width ＋ tileX |
| mineNodes | 全部礦點：id、tileX、tileY、rich、areaId、初始儲量 |
| mineAreas | 全部礦區：areaId、類型（main／expansion／rich）、所屬起點（若有） |
| startSlots | 全部起點：playerId、tileX、tileY（主堡左上角格） |
| watchtowers | 全部瞭望塔：id、x、y（單位座標） |
| me | 自己的 playerId |
| players | 參賽者 playerId 列表 |
| stats | 所有單位與建築的數值表（同本文件） |
| matchSeed | 本場亂數種子 |

### 輔助工具

| 工具 | 說明 |
| --- | --- |
| pathDistance(起點, 終點) | 依尋路規則計算的路徑長度（單位），只考慮地形與目前已知建築；不可達回傳 -1 |
| canPlace(建築代碼, tileX, tileY) | 依地形與目前已知資訊判斷可否放置 |
| terrainAt(tileX, tileY) | 地形代碼 |
| random() | 以 matchSeed 與 playerId 初始化的確定性亂數；選手唯一可用的亂數來源 |

不提供隘口偵測、礦區排序、戰力評估——這些是選手要比的地方。

### 觀察資料（每次決策）

| 欄位 | 內容 |
| --- | --- |
| tick | 目前 tick |
| minerals | 目前礦量 |
| supplyUsed、supplyCap | 已用人口、人口上限 |
| myUnits | 自己的單位：id、type、x、y、hp、stance、group、目前指令、是否攜帶礦、正在採的礦點 id |
| myBuildings | 自己的建築：id、type、tileX、tileY、hp、建造進度、生產佇列、集結點 |
| enemyUnits | 視野內的敵方單位：id、owner、type、x、y、hp |
| enemyBuildings | 視野內的敵方建築：id、owner、type、tileX、tileY、hp、建造進度 |
| rememberedBuildings | 已探索但目前不可見的敵方建築最後狀態，含 lastSeenTick |
| mineNodes | 可見礦點的剩餘儲量；不可見者為最後已知值 |
| watchtowers | 各瞭望塔的佔領者（可見時）與自己的佔領進度 |
| alivePlayers | 仍存活的 playerId（公開資訊） |
| events | 自上次決策以來的事件 |
| knobs | 目前的旋鈕值（可能因戰術暫停而改變） |
| commandBudget | 本次可用的指令額度 |

## 選手 API：指令與事件

決策回傳指令陣列，引擎依陣列順序處理；每個指令消耗 1 點額度，不論對象是一個單位還是一整支部隊。

### 指令

「單位集合」可為單位 id 陣列，或編隊代號 0～9。

| 指令 | 參數 | 說明 |
| --- | --- | --- |
| gather | 單位集合、礦點 id | 工人開始對該礦點採集循環；非工人略過 |
| build | 工人 id、建築代碼、tileX、tileY | 工人前往並建造；座標為建築左上角格 |
| resume | 工人 id、建築 id | 接續未完成的建築 |
| train | 建築 id、單位代碼 | 排入生產佇列 |
| cancel | 建築 id | 取消佇列最後一項；建築本身建造中則取消建造 |
| rally | 建築 id、x、y | 設定集結點 |
| move | 單位集合、x、y | 移動，沿途不主動攻擊 |
| attackMove | 單位集合、x、y | 攻擊移動 |
| attack | 單位集合、目標 id | 攻擊指定目標 |
| hold | 單位集合 | 原地停下，設當前位置為駐守點 |
| stance | 單位集合、姿態代碼 | 設定姿態 |
| group | 編隊代號、單位 id 陣列 | 將單位設為該編隊（覆蓋原內容；單位只屬於一個編隊） |

單位集合中不屬於自己或已死亡的單位自動略過，其餘照常執行。

### 事件

| 事件 | 內容 |
| --- | --- |
| underAttack | 自己的單位或建築受攻擊：受攻擊者 id、攻擊者 id（若可見） |
| unitDied | 自己的單位死亡：id、type |
| buildingDestroyed | 自己的建築被摧毀：id、type |
| enemyKilled | 自己擊殺的敵方單位或建築：id、owner、type |
| buildingComplete | 建築完工：id、type |
| unitTrained | 單位生產完成：id、type |
| nodeDepleted | 礦點枯竭：礦點 id、areaId |
| towerChanged | 瞭望塔易主：瞭望塔 id、新佔領者 |
| playerEliminated | 有選手被淘汰：playerId |
| commandRejected | 指令被拒：指令索引、原因代碼 |

同一 tick 同一對象重複受攻擊只發出一次 underAttack。

### 拒絕原因

| 代碼 | 說明 |
| --- | --- |
| NO\_MINERALS | 礦不足 |
| NO\_SUPPLY | 人口不足 |
| BAD\_PLACEMENT | 位置不可建造 |
| QUEUE\_FULL | 生產佇列已滿 |
| WRONG\_PRODUCER | 該建築不能生產此單位，或建築未完工 |
| INVALID\_TARGET | 目標不存在、不可見或不合法 |
| NOT\_OWNED | 指定的建築或工人不屬於自己 |
| BAD\_FORMAT | 指令格式錯誤 |
| NO\_BUDGET | 超出指令額度 |

## 選手 API：限制、執行模式、確定性與旋鈕

選手受指令額度、時間上限與沙盒限制；回放以「seed ＋ 指令紀錄」重現，不依賴重跑選手程式。

### 指令額度

- 令牌桶：容量 5，每 2 tick 回補 1（每秒 5 個，約 300 APM）；開局額度 5。
- 每次決策可用額度見 commandBudget；超出部分以 NO\_BUDGET 拒絕。

### 時間上限與錯誤

| 狀況 | 處理 |
| --- | --- |
| decide 超過 5 ms（軟上限） | 該次決策的指令全部作廢 |
| init 超過 1000 ms | 選手整場閒置 |
| 任一進入點超過 50 ms（硬上限） | 終止選手，整場剩餘時間閒置（防無窮迴圈） |
| 拋出例外 | 該次視為無指令，比賽繼續；例外內容記錄供除錯 |

### 執行模式

| 模式 | 用途 | 隔離 | 計時 |
| --- | --- | --- | --- |
| 正式模式 | 軍備競賽評測、正式排名 | 每位選手獨立 Worker | 依上表 |
| 批次模式 | 遊戲內練習賽研發、NPC 比賽、大量統計 | 與引擎同一 Worker | 不計時（僅保留硬上限） |

- 正式模式一律在 Node 執行，以標準硬體量測時間。
- 批次模式下，原本會超時的決策會被執行，結果可能與正式模式不同；選手應遠低於軟上限運作。

### 確定性

- 引擎在相同 seed 與相同指令序列下必須產生相同結果。
- 回放保存「比賽 seed ＋ 每次決策的指令紀錄」，不重跑選手程式。
- 選手只能使用提供的 random()；不可使用 Math.random、Date、performance 等非確定性來源。

### 選手模組限制

- 單一 JS 檔案（ES2020），不可 import 其他模組或外部函式庫，≤ 200 KB。
- 無法存取網路、檔案、DOM 或其他選手；選手之間無任何溝通管道。
- 只能透過觀察資料取得資訊；嘗試讀取引擎內部狀態視為違規。

### 旋鈕

- 在 declare 中宣告 3～6 顆旋鈕：代碼、名稱、說明（給玩家看）、最小值、最大值、預設值、整數或小數。
- 範圍內的任何值都必須讓選手正常運作。
- 旋鈕值每次決策透過 knobs 傳入，比賽中可能改變，選手必須能正確應對。
- 同一流派的所有版本，旋鈕代碼與範圍保持一致。

## 參賽須知

你要在時限內寫出一隻能在 1v1 與 4 人混戰中取勝的選手，並符合指定的風格方向。

### 交付物

- 單一 JS 模組，實作 declare、init、decide，符合「選手模組限制」。
- 每次有明顯進步就保存一個版本快照（v1、v2…），附一行變更說明；快照會成為選手的成長線，因此早期版本也必須可正常執行。
- 最終版本與一份簡短說明：策略概要、各旋鈕用途。

### 條件

- 時限：MVP 測試 1～2 小時；正式約 5 小時。
- 風格方向：任務會指定一種，最終版本須明顯體現該風格。
- 最低標準：1v1 對基準 Bot 勝率 ≥ 70%（隨機地圖、至少 50 場、雙方交換起點）。
- 不得針對特定地圖寫死座標。
- 不得利用引擎漏洞；發現漏洞請回報，而非利用。

### 可用工具

- headless 模擬器 CLI：指定選手、對手、規模、場數與 seed，輸出勝負與統計；可輸出回放檔。
- 回放播放器：在瀏覽器中觀看回放。
- 基準 Bot 原始碼，可作為對手與範例。
